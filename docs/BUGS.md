## 当前记录

## Bash smoke 的提前匹配导致生产者 SIGPIPE（2026-10-15）

**现象：** standalone smoke 的原生 Bash 回归偶发退出 141；合法响应首段已包含匹配内容，但 CLI smoke 尚未执行。加入首段匹配后继续写 256 KiB 的 HTTP fixture，可稳定重现同样失败。

**根因：** `set -o pipefail` 下，`grep -q` 找到匹配后提前退出；curl 仍写后续分块时被关闭管道终止。有效的响应内容因此被传输生产者的非零退出误判为失败。

**修复：** 两个 HTTP 检查保留原匹配表达式，使用读完整个流的 grep 并重定向输出；保留 curl 失败和无匹配时的非零传播。回归使用真实 Bash 管道与持续输出的 HTTP fixture，不模拟整条 smoke 的成功。

**教训：** 开启 pipefail 的验证链需要消费完整的生产者输出；不能通过关闭 pipefail 或忽略 curl 退出码规避管道竞态。

## 全量 pytest 期间发生宿主虚拟内存不足（2026-10-15）

**现象：** source `33f56856` 的原生完整门禁实际返回 1：4 failed、6676 passed、15 skipped。失败包括子 PowerShell 未产出报告、Undo 返回 result_unknown、SQLite `integrity_check` 抛 MemoryError，以及夹具 Git 命令返回 128。Windows 同期记录 19 条 Resource-Exhaustion-Detector / 2004 虚拟内存不足事件，包含约 7 GB 的 Python 进程；失败数据库、Git 夹具、原始日志和原生退出码均已封存。

**根因：** 已确认宿主内存压力和一次实际 MemoryError；另外三项的原始异常缺少足够诊断，不能逐项认定同一原因。相同 source 上四项定向重跑全部通过，保存的两个数据库 integrity_check 均为 ok，原失败 Git 目录重跑 ls-files 返回 0。六个空应用的 GC 试验没有显示明显私有内存下降，因此未凭该试验改动产品生命周期或添加全局 GC。

**修复：** 在两端完整门禁增加可选的后端进程隔离模式：冻结全部 catalog，按完整文件串行分组，逐项核对真实执行报告与退出码，并保留 source/index/environment、收集和执行日志的 hash。任意缺测、重复、失败或证据变化都不通过；不会重试失败组或缩减总分母，平台 skip 单列。默认单进程入口及其原失败记录保留。

**教训：** 环境耗尽的失败不能记为产品通过，也不能通过关闭断言、重试或减少测试消除；降低自有执行进程峰值时，仍需证明全量覆盖与失败传播。该模式通过局部验证不等于完整门禁已通过。

## 参数化扩展改变固定安全测试身份（2026-10-14）

**现象：** 来源编码回归的参数化扩展通过局部 pytest，却令真实 catalog 拒绝缺失的固定安全 node ID，S5 影子采集退出 1。对应完整门禁在执行正式评估前主动停止，原生非零回执保留。

**根因：** pytest 为参数化用例生成带参数后缀的身份，替换了固定安全表中的原未参数化入口；文件仍是 p0 不能替代精确 node 身份。

**修复：** 保留原未参数化函数及原场景，新增编码、版本和跨调用矩阵使用独立函数共享断言；旧固定安全表及其 hash 不变，所有新增场景仍按 p0 选择。

**教训：** 扩展固定安全测试时保留原 node，真实 catalog 与固定身份核验应先于最终快照冻结，局部测试通过不能代替它。

## 标题预算测试读取了 worker 完成前的快照（2026-10-14）

**现象：** Agent 与标题各调用一次，但测试保存的 completed 响应仍显示 model_calls=1。

**根因：** 操作完成先持久化，标题随后由同一 worker 预留预算并执行；状态 API 可先返回 completed、worker_done=false。测试检查实时模型计数时标题已执行，却仍使用较早的预算响应。独立检查未发现预算预留遗漏。

**修复：** 测试在标题入口设置事件屏障，明确断言提前 completed 的预算尚未最终稳定；放行后等待 worker_done=true，再核对 Agent/标题调用数及最终预算。产品终态和标题预算策略不变。

**教训：** 用异步 worker 的完成标记核对最终计数，不能将持久操作终态等同于所有附属工作已经结束。

## 作用域授权触发器重建缺少物理事务（2026-10-14）

**现象：** 完整门禁中的双连接抢占测试在线程内出现 `trigger trg_conversations_scope_insert already exists`，但仅统计成功 owner 的断言仍通过。定向负例还证明，DDL 中途失败会丢失旧 guard，另一连接能看见重建时已删除的 trigger。

**根因：** 当前 sqlite3 legacy transaction mode 不会因 DDL 自动 BEGIN；`engine.begin()` 的逻辑事务没有覆盖十个 DROP/CREATE。线程异常也未回传主测试。

**修复：** 仅在十个作用域 guard 的 DDL 块首部显式 `BEGIN IMMEDIATE`，保留原 trigger SQL，由 context 统一提交或回滚。并发测试使用 future 回传两个结果和异常。三项旧实现负例失败，修复后的迁移、scope mutation、mock repository 共 95 项通过，线程异常警告升级为 error 后仍通过；不宣称整个数据库初始化原子化。

**教训：** SQLite DDL 的事务边界必须覆盖实际 driver 行为；并发断言必须证明全部参与者确实执行，不能把工作线程异常当成成功互斥。

## 来源评分只核对种类且遗漏转义原文（2026-10-14）

**现象：** 合成功能反例证明，原 grader 会把撤回后的采集缺失判为 fail；仅剩一条知识来源、笔记版本错误或攻击文本未送达时，最终输入仍可能因存在 `knowledge_context` 而 pass。实际 HTTP MockTransport 负例还显示，嵌套 JSON 的引号和换行使原始子串匹配漏掉来源文本。

**根因：** 来源种类、原文是否选中和具体内容是否进入最终请求未分开核对；观察器缺少笔记版本/原始快照及 JSON 字符串转义对应关系，线程缓存也未绑定模型调用，可能将历史重复文本关联到前次来源。

**修复：** 对应三个 case 升为 v3，新 v5 policy 绑定新 suite；撤回缺采集保留 unknown，E10 按 ID/版本/快照和原文 hash 核对双来源，注入刺激缺失不算通过。投影选择与最终输入绑定 model_call_id、segment_id 和 surface_fingerprint；每次传输后清空临时来源。观察器记录实际请求区间 hash、原文 hash 与编码方式，知识判定还要求完整版本单元实际进入请求，单纯文本匹配仅作诊断。旧 case、policy 和原报告保留。事实代号检查仍不是自动引用质量裁判，实际回答需证据绑定的人工复核。

**教训：** 回答正确和最终数据库未变不能证明必要刺激已送达或整个过程安全；合成题设也不能升级为真实运行证据。

## 新回归误写不可变选测安全版本（2026-10-13）

**现象：** 两项 Runtime 状态回归被直接加入固定 v1 表后，真实 catalog 采集退出 1，报告 `fixed safety baseline changed`；只运行使用微型夹具的选择器测试没有暴露公开文件接线错误。

**根因：** 固定安全表通过代码注册 canonical hash，新增身份也是版本变化；未读注册约束便沿用了旧 baseline_id。

**修复：** 恢复原 v1 的完整字节，注册包含全部 109 个旧身份和两项新回归的 v2，真实 mapping 必须使用 v2。两个版本内容篡改均拒绝，旧文件不删除；两版安全文件修改均触发全集。公开版本回归核对真实 mapping、两版 hash、完整保留关系及禁止降级。

**教训：** 固定策略升级须验证公开配置和真实 catalog，动态夹具通过不能证明发行文件绑定正确；拒绝原地篡改的错误应保留并通过新版本修复。

## Runtime 状态读取拼接不同时间的终态（2026-10-13）

**现象：** 冻结 v10 的 E08 unknown 候选试次第一次 GET 返回 `result_unknown`，worker 结束后同代次返回 `interrupted`，终态稳定断言失败；原始失败保留。独立诊断未发现迟到业务写或第二次执行权限。

**根因：** API 先读持久执行，再读 manager。watchdog 可在两次读取之间通过同一控制器保存 `interrupted` 并将 manager 设为 `result_unknown`；旧的 `running` 行使首个响应采用内存投影。来源可见性也仅在 manager 读取前核对，遗漏期间撤回。

**修复：** manager 读取后回读原精确 generation 的持久记录并重新核对来源可见性，再按 ADR-0010 的持久终态优先规则生成响应。已提交中断仍展示中断；没有改变 manager 未知状态、写入围栏或评分规则。真实控制器超时路径与来源删除交错的两个回归，在旧实现分别得到错误状态和 200 响应。

**教训：** 聚合状态接口需要在内存观察之后验证同一持久身份；单次提前检查不能保证随后返回的状态和可见性仍符合契约。这次回读不提供跨数据库与内存的全局原子快照。

## 公开门禁模板绑定换行规范化前的 suite（2026-10-13）

**现象：** 冻结 v7 的候选 D 57/57 通过、独立审查有效，但原生 initial gate 退出 2，报告 `policy_suite_mismatch`；两个公开模板的实际 checkout 回归均失败。

**根因：** v3 policy 写入的是施工工作文件的 CRLF 字节 hash。随后 suite 已配置 `text eol=lf` 并经 Git 归一化，新 worktree 的 LF 字节 hash 与模板不同；只用动态构造的 policy 单测没有核对公开模板。

**修复：** 新增 v4 initial/release policy，绑定实际 LF checkout 的 suite hash，十九执行项、三次重复、所有安全规则及独立审核要求保持不变。core policy 也固定 LF。历史 v3 和非零报告保留，不改原始结果或放宽 hash 校验。公开模板回归同时检查 suite 字节与 gate 接线，release 缺基线仍 incomplete。

**教训：** 含字节 hash 的发行配置必须在 Git checkout 后核对；工作目录内容与 Git 归一化后的字节不能混用。

## 外部检查导入的引用和 Git 读取边界（2026-10-13）

**现象：** 独立审查发现外部回执草案可接受与命令无关的报告/数据文件，空指标或缺定义的完整性判定不一致；Git 快照可能触发仓库配置中的外部 diff、textconv、fsmonitor 或 clean filter。

**根因：** 文件存在和哈希一致不能替代 command/fixture/capture 绑定；Git CLI 的只读目标不保证没有可配置的执行回调。

**修复：** 严格核对真实命令选项、报告捕获方式与文件、完整 fixture 目录或同检查数据 manifest；缺失指标/定义保持 incomplete，明确非零/失败优先。结构化输入只对同次读取字节校验 hash 后解析。快照清除 Git 环境路由，禁用全部相关回调并将原生 Git 错误转换为配置错误；实际合成 Git repo 的恶意 helper 标记未出现。

**教训：** 外部 attestation 仅说明本地捕获的执行与证据，不能认证作者或进程；始终单列，不升级为 Harness trial、质量结论或发布批准。

## 续流驱动等待终态且未传正确游标参数（2026-10-13）

**现象：** 冻结 v5 的 E07 真实 A/B 都显示 running 时断线、同 generation，但重连接到 `runtime_resync_required`，确定性短块响应没有暴露问题。

**根因：** 驱动释放模型屏障后等待整轮完成才打开续接；真实模型的逐 token 事件超过保留范围；同时驱动误传 `cursor` 而 API 绑定 `after`，原结果没有证明游标恢复。该结果不能当作产品续流退步。

**修复：** E07 升 v3：在屏障仍持有时用实际 cursor 建立 SSE 订阅，再释放模型，记录实际 `after`、接入前置标记及游标之后的 Turn/generation 事件序号；订阅控制帧不能充当恢复事件，有界 resync 须通过原生 snapshot 回读同一身份及覆盖已收事件的高水位。D 增加均匀 300 段的有界分块，覆盖短块模型遗漏的缓冲边界。新增独立 stream-preflight suite 与 v3 policy，旧 v2 原始结果和 reader 保留。本轮有协议缺口的真实运行被停止，所有预留保留；新版双方复验独立报告。

**教训：** 断线、重连与事件保留窗口必须按实际时序验证，不能用终态后拉流替代执行中续接。

## 核心评估误读实际恢复与预算协议（2026-10-13）

**现象：** 首轮 38 项确定性 A/B 运行中，拒绝、租约恢复、SSE 重连及预算项出现双方同型失败；旧证据保留在独立冻结工作树。

**根因：** 拒绝携带空编辑参数；将 Unix 秒租约当 ISO 字符串；仅解析 SSE `id:` 而实际 cursor 在 JSON data；五秒预算在冷启动时未达到故障边界；只观察异常遗漏 Runtime manager 的主动终止。

**修复：** 使用实际 HTTP/租约/cursor 契约；仅 E04 编辑确认；脚本计数跨重启保留；观察真实预算对象及 manager 终止。unknown 屏障绑定 primary 已实际提交、尚未交付结果，释放后核对零迟到 DML 与非成功公开状态。预算按实际资源原因判定，排队执行可以公开 failed。E08 先升为 v2，unknown/deadline 为 60/30 秒、模型/工具限额仍为 2/1。启动缺测后，E01/E04/E06/E08 升为 v3，其余 core 升为 v2：prepared/ready 共用有界 90 秒启动期限，trial wall 为 360 秒、缺回执为 600 秒，增加阶段耗时证据。旧 spec、旧 reader 工作树及失败产物保留；完整 A/B 复验单独记录。

**教训：** 必须证明故障前提已达到；未知前提不等同产品失败。公开响应、内部状态和传输格式分别按真实契约评分，不修改产品时钟或租约来迁就测试。

## 真实流式响应漏采模型与 usage（2026-10-13）

**现象：** 真实查询正确，但供应商响应元数据为空；旧观察器仍给 task pass。正式观察关闭后保留 6 次允许请求的完整费用预留，不据此补零或推定供应商已停止计费。

**根因：** 被测流式路径没有显式请求 usage；观察器按 HTTPX transport stream 标志分流，并在解压前解析 SSE。loopback 总是带 usage 且不压缩，未暴露这两个边界。

**修复：** 显式 `stream_options.include_usage=true`；按 wire 模式读取 JSON 或观察公共 decoded-byte iterator；保留未知 request ID，不用空字符串 hash 冒充 ID；real 必需证据要求发送身份与完整模型/usage 观察匹配。新增 transport-stream JSON、gzip SSE 正反例。重跑前按已关闭 run 的全部预留扣减任务总预算。

**教训：** 任务成功不等于观测完整；必须覆盖供应商的实际传输形态，缺失元数据不能补成零费用或完整证据。

## 命令模块导入返回零却未执行门禁（2026-10-12）

**现象：** 选测器用 `python -m offerpilot.cli` 启动评估或 smoke 时，进程返回 0，却没有实际报告或完成输出。

**根因：** 模块定义 Typer app，但没有 `__main__` 调用；只导入模块不会执行 console 命令。

**修复：** 注册执行命令明确导入并调用 app；Harness 回读冻结 manifest 与原始证据，smoke 核对真实完成标记。真实 CLI、缺报告的 0/3 返回以及正常/故障运行已验证。

**教训：** 退出码 0 必须结合实际门禁完成证据；不能把导入成功当行为验收。

## 恢复回执评分混用内部与公开状态（2026-10-12）

**现象：** 最终跨版本正常评估中，两个 E06 恢复项均被新增回执身份检查误判为失败。

**根因：** 数据库 WriteOperation 使用 `status=committed`，公开 replay response 使用 `write_status=success`；评分器错误要求公开响应使用内部状态。

**教训：** 持久化状态和运输层状态应分别核对；增强评分规则必须用真实成功响应回验。

## 参数化前端断言标题重复导致无法对账（2026-10-12）

**根因：** Knowledge 响应与面试事件契约的 `it.each` 多个输入使用完全相同的标题；JSON reporter 的 `fullName` 无法唯一标识这些断言。

**修复：** 标题补充 Vitest 支持的 `%#` 参数化索引，不改变输入、断言或产品行为。

## 投递读取时间规范化意外触发写入（2026-10-12）

**现象：** Harness 的编辑面试执行项除更新目标事件，还提交了投递 `updated_at` 的变化；单纯绑定 Session 后读取并提交也产生 UPDATE。

**根因：** SQLite 返回不带时区的 UTC。`_normalize_model_status` 用普通属性赋值补上时区，SQLAlchemy 将等价时间视为脏值，flush 时写回 `first_applied_at` 并触发 `updated_at`。

**修复：** 对未被调用者修改的时间属性使用 `set_committed_value` 做呈现规范化；已存在的真实待提交修改保留历史。未修改领域字段、迁移或审批协议。

**验证：** 新回归在修复前明确失败；修复后同时检查读取不产生已提交业务 DML，以及真实时间修改仍能提交。相关应用、scope、事件与 Runtime 回归列于 Harness 验证记录。

**教训：** 绑定事务中的读取辅助函数不得通过呈现转换触发持久化副作用；最终状态相等不足以证明零业务提交。

**验证：** 传输模块 49 项通过；两种传输下 Provider/timeout CAS 及已提交回执 6 项通过；停止和新执行不能被恢复覆盖 2 项通过。传输缺陷先以直接执行与 worker 两种模式复现，再验证修复。

**教训：** 超时撤销 worker 权限与可信终态回执是不同路径；回执必须保持原身份与围栏，传输取消策略不能无差别丢弃已经收敛的事实。

## Runtime 恢复时混用缓存状态与任务身份（2026-09-09）

**现象：** 来源删除后仍可能读取缓存结果；数据库已标记未知的执行可能显示 running；旧任务恢复可能读到同会话后续任务的回复，确认终态也可能带上错误的 Turn 身份。

**根因：** 观察路径过度依赖进程内缓存，恢复按会话取最新消息，确认重放缺少 operation 到 Turn 的绑定检查。容量拒绝发生在接纳持久化之后，启动异常也可能残留 running 记录。

**修复：** 状态、快照和 SSE 重校验来源，数据库已知终态优先；恢复通过持久化 Turn/消息/operation 关联重建结果。确认先校验精确 Turn，再进入拒绝或重放路径。接纳前预留容量，重复请求优先核对原身份，启动失败收敛 lease；进程启动即将旧 epoch 的在途 Runtime 记录标记为未知。

**验证：** 独立审查及 9 项故障回归通过：来源删除、打开中的 SSE 失效、数据库未知状态、错 Turn 拒绝与终态重放、同会话 A/B 驱逐恢复、接纳启动失败、并发重复提交、旧 epoch 围栏。

**教训：** 观察缓存不能覆盖持久化事实；恢复和重放必须保持原任务身份，容量拒绝必须与是否接纳的语义一致。

## Runtime 构造即启动导致空闲线程积累（2026-09-09）

**现象：** 全量测试进程中积累大量空闲 Runtime worker 和 watchdog；仅构造应用也启动线程。

**根因：** manager 构造立即启动固定池，而只构造应用、不进入 lifespan 的调用方没有 shutdown 回调。

**修复：** 构造与容量预约保持无线程；首次有效提交在锁内启动一次固定池，关闭未启动的 manager 安全。启动失败关闭接纳并唤醒已启动线程，不将任务加入无人处理的队列。

**验证：** manager 14 项通过；与真实 API 和接纳围栏组合的 19 项通过，涵盖第二个线程启动失败和首次提交只建一个固定池。

**教训：** 显式启动有工作要消费的资源；应用构造与运行期资源所有权分开，部分启动失败也必须可收敛。

## 知识 Note 修订遗漏旧版本完整性校验（2026-09-09）

**现象：** 损坏 JSON 或已失效的引用可能被修订路径复制；公有读取可能抛出解析错误。

**根因：** 修订只校验编辑命令与版本 CAS，没有验证被复制的旧正文 hash、结构和当前 Evidence/Snapshot 链。

**修复：** 修订与管理读取共用完整性校验，失效版本不再暴露或复制；只回读引用对应的快照区间，不加载整个快照。JSON 总界限按合法块和引用上限计算，避免误删超过 64 KiB 的合法重复引用。

**验证：** 最新知识上下文 10 项通过，包含损坏 JSON、陈旧快照、公开读取过滤、大段合法引用读写；捕获仓库 4 项与相关 mypy/ruff 通过。

**教训：** 新版本确认必须验证旧版本依据；有界校验的总上限必须容纳已有契约允许的合法数据。

## 源码审计重复解析超过时间预算（2026-09-09）

**现象：** 新增前端模块后，生产源码审计从基线 29.6 秒增加到约 38 秒，超过原 30 秒门槛。

**教训：** 规则规模增长时先消除相同输入的重复工作，缓存必须保留输入身份并隔离不同审计。

## 可选来源读取超时与连接池清理（2026-09-09）

**现象：** 临时锁竞争使可选上下文读取失败；连接池替换连接时再次设置 journal mode，会在外部独占锁期间超时并丢失池槽位。

**根因：** 临时不可用与完整性错误共用异常；清理过程重复执行可能获取写锁的 PRAGMA。

**修复：** 仅识别 deadline 和 SQLite 临时锁错误，省略本次可选来源并保留原历史；未知和完整性错误继续失败。替换连接沿用数据库已有 journal mode，避免在清理时读写数据库。

**验证：** 定向 4 项通过，包含真实独占锁、缺表错误不降级、恢复后池容量保持 4；相关 mypy 通过。

**教训：** 可选能力降级必须区分暂时不可用与验证失败；失败清理本身也要受时限和资源守恒约束。

## 新协议续聊遗漏持久化身份与界面路由（2026-09-09）

**教训：** 模块测试通过后仍需从实际产品入口验证身份传递、路由注册和保存结果。关闭重开应只读取原任务，不能新建执行。

## 可选上下文来源与历史轮次边界（2026-09-09）

**教训：** 来源适配测试必须包含真实来源元数据分支；压缩历史必须保持原分组，不只比较文字或总预算。验证记录见 [P3B–P5 计划](superpowers/plans/2026-09-09-harness-p3b-p5-delivery.md)。

## 执行状态跨页面后缺少发送门禁与完成回填（2026-09-09）

**现象：** P3A 审查中发现，Haru 仅从服务端读到 running 时仍可用 Enter 发起请求；执行 A 切到 B 再返回 A 后，旧 stream 完成在展示接口失败时不能回填最终消息。

**根因：** 发送门禁只看本地 loading；旧 stream 的可见代次失效后只刷新会话列表，依赖可选 Timeline 恢复内容。

**修复：** 两个外壳和共享发送入口均检查 running execution；返回原会话后的完成回读持久消息及 Pending，落地前再次核对会话、可见代次和当前请求所有权。返回失败提供错误提示。

**验证：** Haru 远端执行禁用输入、共享发送拦截、后台完成回填及回读期间切换会话均有定向用例；先复现缺失门禁与缺失回读，再验证修复。完整本期记录见 [P3A 计划](superpowers/plans/2026-09-08-harness-p3a-turn-control.md)。

**教训：** 服务端执行状态必须覆盖所有发送入口；可选展示接口不能成为恢复已提交结果的唯一途径。

## 展示失败回退后缺少恢复入口（2026-09-08）

**修复：** 会话所有者暴露按会话隔离的展示失败与刷新状态，Pilot 和 Haru 共用独立恢复提示。重试仅调用展示 GET，进行中禁用按钮，重复失败保留入口，成功后隐藏；旧请求不能覆盖当前状态。

**验证：** 真实 Haru 组件先复现入口缺失，再验证无 Pending / Undo 时的可见按钮、重复失败、禁用防连点和恢复成功；相关前端 49 项、TypeScript、构建与独立 CR 通过，既有大 chunk 提示保留。审查发现的旧卡片和 Pending 刷新入口防连点缺口也已修复。

**教训：** 故障恢复必须从产品可见入口完成闭环，不能仅验证 Hook 暴露的函数可调用。

## 展示刷新失败遮住最新持久消息（2026-09-08）

**现象：** Pilot / Haru 成功加载一次展示后，后续展示请求失败，已保存的新问题和回复仍被旧快照遮住。

**根因：** 失败分支未清除缓存投影，而过期投影只追加 transient 消息，不包含新增持久消息。

**修复：** 当前请求失败时清除展示快照，回退到会话所有者的最新消息；过期请求的失败不影响新请求。请求期间仍保留原操作节点，手动刷新成功后恢复服务端展示。

**验证：** 新增回归先复现失败，再验证持久消息回退、刷新恢复和旧请求拒绝隔离；相关前端 47 项通过。迁移基线为新仓库 `origin/master`，顺序迁入 `608272c → bda0ef7 → ecaa2b5`，对应 `a0e9519f → 478568b3 → 64c988e8`。

构建（含 TypeScript）与独立子代理 CR 通过；内置浏览器在临时数据库、假 Provider 下先加载成功展示，再注入展示 GET 503，拒绝建议后的最新持久回复正常显示。后端代码与迁移前一致，本次未重跑后端全套、完整发布 gate、Docker 或真实 Provider 验收；既有前端基线约束与并发撤销风险仍保留。

**教训：** 快照的加载中保留策略必须有失败出口；首轮加载失败测试不能替代已有缓存后的刷新失败测试。

## 未知录入另建后重开丢失恢复入口（2026-09-08）

**现象：** 未知提交选择承担风险另建后，关闭重开表单不再显示旧提交；新增恢复存储也未与既有隐私审计契约对齐。

**根因：** 常驻表单的 `bypassed` ref 超出单次打开周期；恢复存储直接序列化开放的运行时对象，审计没有获批恢复流程的限定规则。

**修复：** 每次打开清空跳过标记；读写恢复记录校验工作区、请求键、封闭字段和类型，拒绝凭据及额外参数。审计仅认可已审查适配器的固定路径与内容摘要，保留全局敏感存储检查和负向测试。

**教训：** 关闭、重开与刷新是不同生命周期，均需验证未知结果仍可恢复。获批本地恢复不是持久化任意 AI 状态或凭据的许可。

## 单条录入衔接中的来源读取与导航缺口（2026-09-08）

**现象：** 开启工作区鉴权时 JD 请求缺少访问令牌；历史保存时间没有时区；新建或重复提示返回的投递若不在列表缓存中，无法立即打开准备页。

**根因：** JD service 独立调用 fetch 未复用 auth headers；SQLite UTC 时间直接序列化为无时区字符串；详情导航只从列表缓存解析身份。

**修复：** JD 请求使用现有 authHeaders，历史时间按 RFC3339 标记 UTC；新增入口在导航前纳入返回身份并保留后续列表重取。关闭表单后的旧异步回调增加代际检查，避免意外导航。

**教训：** 创建成功、列表刷新和资料读取是三个独立结果，必须分别验证恢复路径。来源字段不因此变成可访问的网址；令牌只用于本地 API，不写入草稿或来源。

## 用户修改确认参数后，模型建议改回旧值（2026-09-07）

**状态：已实现确定性回执边界；验证与限制见 [P0 记录](../artifacts/2026-09-08-harness-p0/verification.md)。**

**现象：** 用户把签字费从10000改为8000、远程办公从两天改为一天并批准后，模型仍可能把新值解释为保存错误，建议恢复原请求。

**根因：** 续答已有实际批准参数和工具结果，但缺少“差异来自用户主动修订”的明确语义；原始用户请求仍在上下文中，模型可能错误地把旧请求当作最终意图。

**修复：** 用户合法修改参数且规范化后与原提案不同、Ledger 可靠证明提交成功时，结束本次确认后的模型续答。回执从原终态结果构造，与 ToolMessage 原子保存；策略绑定原操作、请求指纹与结果摘要，重启恢复和重复确认不再进入模型。原提案、HITL、Undo 和独立新请求保持可用；等价编辑与失败沿用原分支。决定见 [ADR-0006](architecture/decisions/0006-edited-confirmation-receipts.md)。

**实际验收：** 之前两版提示词各有一次真实样本反向，最严重样本生成恢复旧值的 Pending。本次可控测试先在旧代码证明额外模型调用，再验证成功编辑后的零调用与独立进程恢复。真实模型固定两个隔离 Offer：初轮仅文字确认，在原对话各补一次明确确认后均进入系统 Pending；编辑为 8000/一天后，sync/SSE 和交叉重放通过，总调用 6 次（上限 8），确认阶段零调用。首轮结果全部保留，不隐去未进入 Pending 的情况。

**教训：** 需要确定性保证的确认边界必须由可信业务事实控制，不能依赖模型措辞。业务提交成功与回执交付必须分别恢复，不能直接返回未保存的成功字符串。停止自动续答仅适用于本次成功编辑确认；模型文字二次确认、虚构按钮和多入口展示属于独立问题。

手动 mutation 只失效题库而非 due 缓存；表单未关联预填；独立来源查询的加载状态被解释为领域不可用；展示层复用机器路径/错误状态域。Runtime 校验原提案后未将实际批准参数投影到 continuation，且 `None` 的 Undo 更新语义为保留旧值。

### 修复
新增/编辑/删除同时刷新 due；新建 Offer 按字段预填并保留手改；未可执行任务等待来源查询完成；日期/时长缺失明确展示。路径只做中文展示，原证据身份不变；根级 import_review 不进入新候选/新选择，但历史证据仍可重校验。确认续跑仅修改脱离持久化的消息副本；成功/失败无 Undo 用空对象清旧 owner，拒绝仍保留原 Undo。撤销错误显示冲突或核对结果提示，不放宽 CAS。

### 教训
缓存依赖、加载态与不可用态、展示身份与执行身份必须分离。保留原提案审计与历史证据兼容。Undo 更新必须区分保留、清除和替换。组件回归、sync/SSE 确认集成及历史来源重校验覆盖上述边界。

### 尚未关闭
U01 模型文字二次确认/备注能力描述、U02 unknown_tool、U05 标签页崩溃、U10 谈薪算术与擅自承诺、U12 请求中止/结果待确认尚无足够根因证据。本次不改变模型策略、不自动重试、不撤销未知结果，不宣称全部走查问题已解决。历史已失效的 Undo 数据不批量重写。

## 日程时区偏移（2026-09-07）

**现象：** Pilot确认15:00后，日历显示23:00；带非零offset的API输入亦受影响。

**根因：** SQLite DateTime丢弃offset而保留wall time；仓库未先换算UTC，API回读又给无时区值补UTC。页面通常提交Z时间，因而掩盖了另一入口的问题。

**修复：** 日程仓库普通/绑定/scoped创建和更新统一将scheduled_at、remind_at换算成UTC再写入；naive保留既有UTC含义，参数原文、事务所有权和Provider契约不变。未对无法恢复原始offset的历史行做批量迁移。

**验证边界：** 新增东八区、负offset、跨日、UTC、naive、提醒和回滚测试；API覆盖创建/更新/列表回读。复现用例先在旧实现出现8个偏移失败。模型虚构按钮或误解用户修订是独立回复质量问题，不属于本条修复。

**教训：** 以存储边界保存同一时刻，不只在显示层做时区转换；同一功能必须覆盖页面与工具输入的不同时间编码。

## 多标签页覆盖待恢复提交（2026-09-08）

**现象：** 两个标签页同时更新待恢复提交时，后写入的数组可能覆盖另一个请求，导致恢复入口丢失；不会因此自动重复执行请求。

**根因：** `chatSubmission.ts` 将所有请求存放在一个 localStorage 数组，增删和接纳更新均先读后写。localStorage 单次写入原子性不能保证整个读改写过程原子。

**修复：** 按 request ID 独立保存恢复身份，每次只修改对应键。旧数组保持只读；对应独立记录覆盖旧值，删除旧请求用无正文标记抑制旧入口。快照按 ID 排序以保持 React 订阅稳定；存储不可用时保留本标签页内存恢复。

**验证：** 在第一个标签页写入前确定性插入第二个标签页新增请求，覆盖新增、标记接纳、删除请求及按会话删除四种交错；旧实现全部丢失第二个请求，修复后均保留。另覆盖旧数据重新加载、跨标签事件订阅、稳定快照和存储写入失败。

**教训：** 多标签页共享的集合不要通过全量读改写维护独立请求；请求幂等执行与客户端恢复入口持久化需要分别验证。

**剩余边界：** 本修复隔离不同 request ID 的写入。同一 ID 在两个标签页并发接纳和遗忘仍可能留下多余恢复入口；这是只读恢复提示，不会触发自动执行。暂不为此引入永久终态标记或异步事务存储。

## PowerShell 门禁在原生命令失败后仍显示通过（2026-09-10）

**现象：** pytest、前端构建、`oc smoke` 或可选子门禁返回非零退出码后，PowerShell 发布入口仍继续执行并显示 `Release gate passed`；发布入口与 local smoke 还会重复构建前端。

**根因：** `$ErrorActionPreference = "Stop"` 不会自动把 Windows PowerShell 原生命令的非零退出码变成终止错误；父脚本也未检查子 PowerShell 的退出码。local smoke 无复用本轮成功构建的显式参数。

**修复：** 发布、local smoke、安装及 Docker PowerShell 入口逐项检查原生退出码并终止；Shell/PowerShell local smoke 默认构建，发布入口只在构建成功后传 `--skip-build` / `-SkipBuild`，跳过时仍要求存在 `web/dist/index.html`。真实 CLI 启动、HTTP、HITL 与业务 smoke 覆盖保留。

**验证方式：** 隔离命令夹具执行实际门禁脚本，注入各步骤非零退出码，验证停止后续步骤、父入口非零且无成功提示；同时覆盖单次构建、独立 smoke 默认构建、缺产物与参数传递。修复前已复现失败仍显示通过和双构建。

**教训：** 成功日志不是成功证据；每层脚本必须传播失败。构建产物存在不等于匹配当前代码，复用需要同一成功构建的上下文。

**同轮走查补充：** PowerShell local smoke 原先只停止启动器，真实通过或启动超时后均可留下 uv/oc/Python 子进程。改为清理本次启动器的进程树、限时等待退出，始终恢复调用者数据目录环境；清理失败不显示通过。回归覆盖成功/失败后的清理和清理本身失败。首次新虚拟环境冷启动曾在依赖字节码写入时超时，保留失败记录，不调整健康检查超时。

## 获批基线复用时比较了未获批的 A 分组（2026-10-13）

**现象：** 一个 A/B 运行晋升的是 candidate 分组。发布预检允许复用同一运行时，相对门禁仍因 run_id 相同选择原 baseline 分组，可能将候选与自身的复用错误报告为修复或不可比较。

**根因：** 通用比较器的 same-run 默认语义是 A 对 B，正式门禁未传入获批分组身份。

**修复：** 通用比较器保留直接 A/B 比较的默认行为；正式门禁的原始及人工复核比较显式使用获批运行的 candidate 分组，并在报告中记录双方分组。不存在的分组拒绝比较。

**验证：** 合成回归覆盖 A 失败/B 通过的获批复用、candidate-only 复用、预检到执行与回执重校验，以及原直接 A/B 的 fixed 判定。合成审批夹具不表示实际维护者批准。

**教训：** 实验运行身份与获批结果分组身份应同时绑定；同一 run_id 不能替代晋升分组的明确选择。

## Windows 平台元数据初始化被评估隔离层误判（2026-10-13）

**现象：** 冻结的确定性 E08 运行记录到 `platform.machine → uname → win32_ver → _syscmd_ver` 的进程尝试，导致 authorized_deltas 失败。该路径是 Windows 在 WMI 不可用时读取系统版本的本地 `ver` 回退。

**根因：** 中性启动器先安装进程审计围栏，后续依赖首次读取平台信息时才填充标准库缓存，可信环境初始化因此被归为产品进程越界。

**修复：** 在安装围栏前预热 `platform.uname()`。安装后的进程、网络及存储限制保持原判定；历史失败记录不改写。

**验证：** Windows 新进程回归在公开 win32_ver 接缝注入相同的 subprocess.Popen 审计事件，证明元数据预热不被拦截，而安装围栏后的 os.system 仍被拒绝。37 项 core integrity 测试、Ruff 与 bootstrap mypy 通过；此回归不依赖实际 WMI 或执行 shell。

**教训：** 隔离初始化须区分可信平台准备与产品执行，不能通过放宽产品进程权限消除环境误判。

## 超时写入竞争让迟到清理把未知结果改为失败（2026-10-13）

**现象：** E08 的主业务修改已经提交，真实运行 deadline 将任务公开为 result_unknown；释放迟到结果后，公开状态可能变为 failed。原始冻结观察保留，不能因为没有额外业务 DML 就把该状态变化判为通过。

**根因：** 超时控制先以零等待 try_finish 尝试写 interrupted，SQLite 忙锁可使其未成功。Durable control 的 finally 只按较长租约判断终态，忽略已发生的 TIMED_OUT，随后将仍为 running 的持久行写成 failed。只在等待数据库锁前采样状态仍有竞争窗口。

**修复：** 仓库取得写锁并核对同 owner/Turn/generation、仍有效的 running 行后才解析终态。控制器用短 CAS 领取完成权；超时先赢时始终选择 result_unknown，完成先赢时 watchdog 不再广播超时未知。数据库锁等待不持有控制器锁；超时初次探测仍为零等待。已结束或过期的行、恢复 scope 和业务提交围栏沿用原约束，worker 自身的超时异常仍收敛到 unknown。

**验证：** 三种迟到终态及 watchdog 完成竞争分别在旧实现复现失败；70 项 control、manager、event-sink 回归通过，含真实 SQLite 写锁竞争、首个探测未成功、正常 completed/failed、旧终态不覆盖和物理 worker 异常收敛。Ruff、相关四模块及全库 228 文件 mypy 通过。端到端及完整门禁结果见本轮冻结验收记录。

**教训：** 较长的执行租约不能替代较短的产品 deadline；终态决定必须与超时控制有明确先后关系，且不得让超时等待业务数据库锁。
