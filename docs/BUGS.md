## 评测预算中断不能降级已观察的 HTTP 失败（2026-10-30）

**现象：** `3b17e669` 综合独立审查发现，首个 legacy 请求的无关 502 若与预算拒绝时间重叠，会从 grader 使用的 `product_failure` 字段移出，导致已知失败被降为 incomplete。真实 `run_trial → seal → grade` 回归在修复前复现两处失败。

**根因：** 同一 trial、epoch、拒绝行及时间窗口只能证明预算拒绝，不能证明该 HTTP 502 的原因。最终进程退出证明也不能补足这种因果绑定。

**修复：** 删除 HTTP 失败的事后重分类。仅正式绑定的离线 targeted simulation 拒绝允许发起客户端请求取消；请求 helper 在同一锁内封存响应头或取消回执。响应头先到则保留原请求等待和结果；取消先到才停止该自有 helper，退出后排空私有管道，晚到的已观察错误状态仍优先判失败。每请求随机密钥只经 helper 私有 stdin 传递，用不同域的 MAC 认证取消与递增进度回执；Windows 实时读取认证档案，终态与私有管道逐条核对。档案独占创建，取消文件独占准备后无覆盖发布，不跟随目标替换路径写入旧文件。

**边界：** 没有观察到的响应仍为 null，缺回执、错绑、档案改写或未证明自有进程树退出不能认证为干净中断。锁内回执顺序不等于物理收包顺序，取消客户端也不证明服务端没有处理 POST。保留原始失败及未知；真实 Provider、HITL、case、grader、重试和原期限不变。相关回归覆盖已知失败优先、取消竞态、回执认证和文件覆盖保护，正式评测与完整 gate 另行记录。

已在私有管道完成的 HTTP 终态先于新的取消处理，不因 helper 尚未退出而丢弃；自行非零退出或退出码未采集仍阻断成功。清理失败及后续期限耗尽不能抹去此前已收到的错误状态和正文；成功结果接受及自有 helper 清理仍服从原期限。

提前读到终态后仍在 helper 退出时排空完整私有管道。迟到成功保持超时；已绑定请求的完整错误响应作为失败保留，并用 `result_observed_before_deadline=false` 明确标出时间范围，不称为期限内完成。

## 评测预算拒绝后的 HTTP 502 被误归为产品失败（2026-10-30）

> 历史修复记录：以下 `3b17e669` 的时间归因方案已被上方取消仲裁修复替代，不能作为当前失败重分类依据。

**现象：** `2687fd09` 完整本地 gate 的 27 请求边界负例已允许并观测到 27 次 loopback 请求，第 28 条预 ACK 预留被拒绝。Legacy epoch 的控制 seq48 已落盘，最后 ACK 为 seq47；控制读取停止后 `/api/chat` 返回“control ACK missing”502。原报告因此为 product_failed／fail／exit1，而预算中断应保留 incomplete／exit3。原失败及 230 份原始文件保留，不涉及付费 Provider。

**根因与边界：** RunLedger 持久化拒绝行后只抛通用 TimeoutError，CoreSubject 丢失异常对象和拒绝来源；HTTP 状态错误又全部用 ProductFailure 表示。本次同步 HTTP 等待读到了该 502，暴露了控制拒绝与普通 HTTP 错误混用的归因缺口。此记录不解释全部历史连接失败，也不回填 legacy 缺失的 execution／request_id。

**修复：** 持久化拒绝后生成带白名单事件、拒绝行及 ledger 身份的 TimeoutError 子类，由同一 CoreSubject 保留；等待队列继续原 TimeoutError 类别。HTTP 状态错误携带 parent-only driver、请求索引、trial／epoch 和时间窗口，不复制正文。仅在 simulation-only targeted 场景中，于清理后确认 reader 和自有进程树均已退出，再核对同一 ledger／subject／driver、epoch 唯一首个请求、完整拒绝行及哈希、事件身份、ACK 恰为拒绝序号减一，才将对应 chat／confirm 502 记为“评测中断、功能归因未知”。原 HTTP 响应和错误文字另存，控制收口不足仍为未知。普通真实运行、缺绑定、并发或多个请求、其他 HTTP 状态及语义 ProductFailure 保留失败。预算、重试、HITL、case、grader 和原 4 秒门槛均不变。

**教训与验证边界：** 拒绝发送不能借 API 错误反推产品能力；观察不足也不能覆盖已知语义失败。局部回归分别保护拒绝持久化、Timeout 等待语义、来源错绑拒绝及 HTTP 原证据；同一快照的真实 loopback 边界、完整正式评测、完整 gate 和独立审查分别留档，未完成前不声明发布通过。

## 子进程退出先于最后控制回执发布，误判关闭失败（2026-10-29）

**现象：** `0a5dc089` 的正式 D57 为 30 pass／27 incomplete：`E08.runtime_unknown` 第二轮的功能目标、授权变更和晚到结果围栏通过，但 `shutdown.wait` 报 DriverError；后续 26 项因关闭未验证而保留 not_run。控制文件已封存 `shutdown_complete`（seq343），读线程最终正常 EOF，无 error 帧，旧结果及该快照 1,962 份源文件原始字节均保留。

**根因与边界：** Subject.wait 在队列短暂无消息时只要发现子进程已退出就失败，没有等仍在落盘、发布最后控制帧的读线程排空。受控线程顺序已复现退出先于回执入队的竞态；原失败在关闭期限附近是否另有延迟仍需新运行区分，不能把原 incomplete 改成通过。

**修复：** 子进程退出后，仍在原 wait／trial 截止时间内消费活跃读线程；读线程结束后再次检查已入队回执。过期后才观察到的回执也拒绝；没有回执继续报错，读线程卡住仍在原期限超时，不额外增加宽限、重试、进程权限或业务确认。原 case／关闭预算和 4 秒流式确认阈值不变。

**教训与验证边界：** 进程退出不等于控制管道已排空。回归覆盖两个 Subject 类型的退出与发布顺序、缺失回执和读线程停滞；真实 loopback 定向检查及新快照完整正式评测分别留档，单元测试不能替代它们。付费验证继续等待确定性和控制闭环，不复用失败运行的部分结果。

## 正式评测的同步响应等待早于产品预算，流异常缺少消费期观测（2026-10-29）

**现象：** v7 `E06.legacy_missing` 第三轮在初次 `/api/chat` 等待约 30 秒后发生本地 `ReadTimeout`；两次 Provider 请求均收到 HTTP 200 响应头，第二次没有 usage／model_result。正式确定性评测另有两项仅记录 pre-trial `ValueError`。失败、原始 incomplete 和费用预留保留。

**根因与边界：** CoreHTTPDriver 对所有请求固定使用 30 秒 HTTP phase timeout，而被测产品同步 chat／confirm 等待 120 秒，存在提前切断合法等待的契约缺口。SSE 迭代发生在 send 返回之后，外层异常捕获不能观测读取期失败；run_plan 只保存异常类名，丢失失败阶段及原因链。历史响应体延迟和两个 ValueError 的具体原因仍未知；不能据此归因为 Provider、DNS 或 Git，也不证明提前切断是全部历史失败的唯一原因。

**修复：** bootstrap 从被测 API 路由实际引用的常量报告同步等待。只对两个阻塞 POST 使用该预算及独立 1 秒终态 HTTP 回复余量，且受原 trial deadline 减进程清理预留限制；异步提交、GET 及其他请求继续原 30 秒上限。单个本地 HTTP owned worker 在绝对截止时间后整树终止并核验退出，避免依赖协程合作取消，拒绝晚到结果、不重发；本地 token／正文经 stdin，响应头进度仅归档身份和时序。新增 Provider 元数据观测分别记录响应头、usage、SSE DONE、自然 EOF、消费端关闭、读取异常和部分行，字节原样传递，不归档正文；超出观察容量只留缺口，终态缺失不能计为完整观测。pre-trial 诊断旁录阶段、完整样本身份及有界脱敏原因链；已经启动的异常另存 eval_error／incomplete 及原始部分证据引用，停止发送后续试次，保留全计划分母。Provider 45 秒、产品 120 秒、case／grader／HITL 均未修改。

**教训与验证边界：** phase timeout 不等于总墙钟；HTTP 200 或 usage 也不等于全流完成。离线反例及传输回归覆盖慢速分块、分阶段延迟、晚到结果、SSE 终态区别和来源漂移拒绝；正式评测、真实 Provider、完整 gate、独立审查和新样本人工结论分别另存，完成对应范围前不声明发布验收通过。新增观测只能证明新运行，不能回填历史归档。

## 短句中的附带行动没有明确指向同一成果（2026-10-29）

**现象：** v7 新复核的 15 条回复确认 12 pass／3 fail，三项均把用例设计与另一项项目或缺陷讲述放进同一短句。原请求只要求每行一个短句，没有“两条建议”的配额。原确认方法、分数、失败原文与其他通过样本保留。

**根因假设与边界：** 实际输入已有独立成果指导，不能归因为漏传提示。模型仍按共同话题合并可分别完成的成果；原指导没有在组织句子时明确附带说明应指回同一份具体产物。这是可改进的表达边界，不证明是模型越界的唯一原因。

**修复：** 共享短句策略先确定每句交付的具体成果，附带说明明确指向它本身的内容或用法，不能仅凭话题相同并入。以活动清单及其依据为正例，以清单和另一段介绍为反例；不植入面试参考答案、不按字词或动词计数、不后处理输出。用户明确任务、详细回答、事实限定和 HITL 保留。

**教训与验证边界：** 模拟模型回归只证明策略进入最终输入，且 HTTP／SSE／数据库原文未被修整；不能据此确认真实模型质量。新版本必须保留 R04 两次回复的各自身份并重新送审，旧确认不迁移。

## 短句准备建议仍笼统并列多个准备方向（2026-10-29）

**现象：** v6 真实 Runtime 的 R04 首轮第一次回复仍在同一句中安排测试用例设计准备与接口自动化脚本练习。原请求是每行一个短句，没有要求“两条建议”配额。两种准备可以分别完成，原样本及待确认的 AI 反例另存；其余新回复不能沿用 v5 标签，也不能因两行格式正确而自动判质量通过。

**根因假设与边界：** 实际输入已经收到按独立成果区分行动的策略，仍有越界反例，不能再归因为提示漏传。只有岗位背景时的通用建议指导仍偏向准备方向，没有在这一处明确先选定一个具体成果；这与回答笼统并列多个方向相符，尚不能证明是唯一原因，也不能用提示增补保证模型稳定遵从。

**修复：** 在缺少 JD／简历的准备建议指导附近，条件化说明：同时要求短句时，每行先选一个具体、可单独完成的成果，不把多个可分别复习或练习的方向统称为“准备”；相关内容只支撑这一成果，其他非必需独立目标再分配或取舍。保留用户明确要求的任务、详细回答、事实边界及 HITL，不绑定岗位、场景编号或参考答案，不修整原输出，不改变重试、评测规则或阈值。

**验证边界：** v6 原始 trial、额外 HTTP 超时、AI 观察和全部旧人工记录保留。局部回归只保护策略进入输入及原文传递；新真实回复、正式确定性评测、完整本地 gate 和人工确认分别记录，未完成前不宣称质量修复或发布验收通过。

## 短句策略未区分同一成果与独立任务（2026-10-29）

**现象：** current-v5 的 15 条回复经用户授权采纳新的 AI 初评后为 8 pass／7 fail，失败为 R01 三轮及 R04 第一、三轮的两次回复。实际输入已经包含“每个短句只保留一个核心意思”，但回答仍把项目讲述与代码练习、额外追问或反问准备合并。R04 第二轮两次回复通过，同一准备成果中的相关主题和范围限定不因此失败。原初评、确认方法及失败原文均保留；“已确认”不表示独立人工逐条复核。

**根因假设与边界：** 原策略已要求取舍，但没有说明“独立行动”的任务边界。模型把共同服务于面试准备的不同成果压成一句，与该说明缺口相符；离线输入、回复及对照样本不能证明这是唯一原因。此前模拟模型测试只证明策略送达和原文保留，不能证明模型稳定遵从语义约束；此前偏宽的 AI 初评也不替代本轮已采纳的失败结论。

**修复：** 共享短句指导按能否分别完成、单独使用的准备成果区分行动；保留同一成果内部的主题、必要步骤、依据和范围限定。用非面试领域、含相同连接词的正反例说明一份报告梳理与另一份学习计划的区别，要求发送前内部检查并取舍第二项独立任务。用户明确要求的任务先分配到可用行数，不作为次要建议删掉。不按字数、动词或连接词计数，不绑定评测答案，不改写输出、自动重试、放宽规则或改变 HITL。用户要求详细展开的回答继续使用原结构。

**验证边界：** 原 v5 七条失败是本次修复前的真实反例；现有同步／流式、旧记忆／撤回及来源相关回归用于保护模型输入与原文绑定，真实 Runtime 的新回复另存并重新评审。局部回归不证明模型质量通过；新快照正式评测、完整门禁与精确基线审批分别留档，旧质量标签不迁移。

## 短句要求下把多项独立行动压进一行（2026-10-29）

**现象：** current-v4 的真实 `E09.memory_override` 第二轮虽输出两行，但第二行同时要求自我介绍、项目复盘、说明角色／方法／结果及确认面试安排。用户确认该回复质量 fail；其余 14 条质量标签、51 项必需过程目标 pass 及 12 项非必需原始文本归档 abstain 分别保留，原 R39 的 27 pass／12 incomplete 和退出码 3 不改写。

**根因与证据边界：** 封存的实际输入已包含当前两行短句要求、旧五段偏好及系统中的“不堆叠长串并列行动”。当前要求已到达模型，物理行数也正确；不能再归因为漏传提示或空行。回复以合并多项行动保留覆盖面，没有完成短句所需的内容取舍。现有提示只描述输出外观，缺少优先选择核心意思、删减次要内容的做法；这是可修复的提示策略缺口，模型为何在同配置的三轮中仅一轮越界仍未知。

**修复：** 在共享回复策略中明确：用户要求短句时，每句保留一个核心意思，通过取舍删减来缩短，不用并列清单或连接词挤入多项独立行动。用户要求详细展开时不受此限制；事实限定、安全和 HITL 继续保留。不绑定场景编号、岗位、固定条数或任意字数上限，不截断、合并、重写原模型输出，不自动重试。

**验证边界：** 同步和流式 API 的中英文请求回归检查当前请求、实际旧记忆及共享策略均进入最终模型输入，并确认畸形模型回答的增量、终态和持久化原文不被修整。局部测试只证明策略传递及原文保留，不能证明模型短句质量；新模型样本另存并重新人工裁定，旧标签只绑定原输出。受影响真实验收、正式评测和新快照完整门禁单独留档。

## AI 调整日程时清空未提供的可选字段（2026-10-28）

**现象：** 真实 `E02.runtime_clarify` 三轮均正确选定技术面、澄清并经确认将时间改到目标时刻，但同时把原 `subtype=technical` 改为空串。实际 Pending 与执行参数未提供 subtype；原业务规则将额外已提交变更判 fail，结果保留。

**根因：** AI 更新工具复用创建参数的解析默认值，省略的 subtype、tags、round、location、notes、remind_at、status 被转换成空值或 todo；scoped repository 随后将所有数据字段写入。确认了原始参数不代表授权这些隐藏默认写入。此前的确定性成功不能证明可选字段省略时仍能保留原值。

**修复：** AI 更新额外传递原始参数中实际存在的数据字段集合，保留原解析校验；scoped UPDATE 只对该集合生成 SET 列，tags 映射到实际存储字段。省略列留在数据库，避免先读整行再全量覆盖确认期间的其他改动；显式空串、空数组、0 和可清除提醒仍执行对应清空。原 scope、active-parent、事务所有权及 HITL 不变。未提供字段集合的原 repository 调用和创建保留原行为；REST PUT 继续全量替换。

**教训与验证边界：** 字段 presence 要保留到 SQL 边界，不能把省略与显式清空混为一谈。局部回归检查同步／Runtime 的确认前无写、确认后省略字段保留、显式及编辑确认清空、确认前独立备注保留，以及 scoped 列集合、跨范围拒绝、非法列拒绝和回滚。原 trial 不回填改分；新快照真实模型、正式评测、人工审阅与完整 gate 各自记录，局部回归不替代发布验收。

**现象：** 全量测试进程中积累大量空闲 Runtime worker 和 watchdog；仅构造应用也启动线程。

**根因：** manager 构造立即启动固定池，而只构造应用、不进入 lifespan 的调用方没有 shutdown 回调。

**修复：** 构造与容量预约保持无线程；首次有效提交在锁内启动一次固定池，关闭未启动的 manager 安全。启动失败关闭接纳并唤醒已启动线程，不将任务加入无人处理的队列。

**验证：** manager 14 项通过；与真实 API 和接纳围栏组合的 19 项通过，涵盖第二个线程启动失败和首次提交只建一个固定池。

**教训：** 显式启动有工作要消费的资源；应用构造与运行期资源所有权分开，部分启动失败也必须可收敛。

## 知识 Note 修订遗漏旧版本完整性校验（2026-09-09）

**现象：** 损坏 JSON 或已失效的引用可能被修订路径复制；公有读取可能抛出解析错误。

**根因：** 修订只校验编辑命令与版本 CAS，没有验证被复制的旧正文 hash、结构和当前 Evidence/Snapshot 链。

**修复：** 修订与管理读取共用完整性校验，失效版本不再暴露或复制；只回读引用对应的快照区间，不加载整个快照。JSON 总界限按合法块和引用上限计算，避免误删超过 64 KiB 的合法重复引用。

**验证：** 最新知识上下文 10 项通过，包含损坏 JSON、陈旧快照、公开读取过滤、大段合法引用读写；捕获仓库 4 项与相关 mypy/ruff 通过。

**教训：** 新版本确认必须验证旧版本依据；有界校验的总上限必须容纳已有契约允许的合法数据。

## 源码审计重复解析超过时间预算（2026-09-09）

**现象：** 新增前端模块后，生产源码审计从基线 29.6 秒增加到约 38 秒，超过原 30 秒门槛。

**修复：** 每次审计创建独立解析缓存，仅同路径且文本完全一致时复用；退出时恢复前一层缓存，fixture 之间不复用。

**教训：** 规则规模增长时先消除相同输入的重复工作，缓存必须保留输入身份并隔离不同审计。

## 可选来源读取超时与连接池清理（2026-09-09）

**现象：** 临时锁竞争使可选上下文读取失败；连接池替换连接时再次设置 journal mode，会在外部独占锁期间超时并丢失池槽位。

**修复：** 仅识别 deadline 和 SQLite 临时锁错误，省略本次可选来源并保留原历史；未知和完整性错误继续失败。替换连接沿用数据库已有 journal mode，避免在清理时读写数据库。

**验证：** 定向 4 项通过，包含真实独占锁、缺表错误不降级、恢复后池容量保持 4；相关 mypy 通过。

**教训：** 可选能力降级必须区分暂时不可用与验证失败；失败清理本身也要受时限和资源守恒约束。

## 新协议续聊遗漏持久化身份与界面路由（2026-09-09）

**教训：** 模块测试通过后仍需从实际产品入口验证身份传递、路由注册和保存结果。关闭重开应只读取原任务，不能新建执行。

## 执行状态跨页面后缺少发送门禁与完成回填（2026-09-09）

**验证：** Haru 远端执行禁用输入、共享发送拦截、后台完成回填及回读期间切换会话均有定向用例；先复现缺失门禁与缺失回读，再验证修复。完整本期记录见 [P3A 计划](superpowers/plans/2026-09-08-harness-p3a-turn-control.md)。

**教训：** 服务端执行状态必须覆盖所有发送入口；可选展示接口不能成为恢复已提交结果的唯一途径。

## 展示失败回退后缺少恢复入口（2026-09-08）

**教训：** 故障恢复必须从产品可见入口完成闭环，不能仅验证 Hook 暴露的函数可调用。

## 展示刷新失败遮住最新持久消息（2026-09-08）

**现象：** Pilot / Haru 成功加载一次展示后，后续展示请求失败，已保存的新问题和回复仍被旧快照遮住。

**根因：** 失败分支未清除缓存投影，而过期投影只追加 transient 消息，不包含新增持久消息。

**修复：** 当前请求失败时清除展示快照，回退到会话所有者的最新消息；过期请求的失败不影响新请求。请求期间仍保留原操作节点，手动刷新成功后恢复服务端展示。

**验证：** 新增回归先复现失败，再验证持久消息回退、刷新恢复和旧请求拒绝隔离；相关前端 47 项通过。迁移基线为新仓库 `origin/master`，顺序迁入 `608272c → bda0ef7 → ecaa2b5`，对应 `a0e9519f → 478568b3 → 64c988e8`。

构建（含 TypeScript）与独立子代理 CR 通过；内置浏览器在临时数据库、假 Provider 下先加载成功展示，再注入展示 GET 503，拒绝建议后的最新持久回复正常显示。后端代码与迁移前一致，本次未重跑后端全套、完整发布 gate、Docker 或真实 Provider 验收；既有前端基线约束与并发撤销风险仍保留。

**教训：** 快照的加载中保留策略必须有失败出口；首轮加载失败测试不能替代已有缓存后的刷新失败测试。

## 未知录入另建后重开丢失恢复入口（2026-09-08）

**现象：** 未知提交选择承担风险另建后，关闭重开表单不再显示旧提交；新增恢复存储也未与既有隐私审计契约对齐。

**根因：** 常驻表单的 `bypassed` ref 超出单次打开周期；恢复存储直接序列化开放的运行时对象，审计没有获批恢复流程的限定规则。

**修复：** 每次打开清空跳过标记；读写恢复记录校验工作区、请求键、封闭字段和类型，拒绝凭据及额外参数。审计仅认可已审查适配器的固定路径与内容摘要，保留全局敏感存储检查和负向测试。

**教训：** 关闭、重开与刷新是不同生命周期，均需验证未知结果仍可恢复。获批本地恢复不是持久化任意 AI 状态或凭据的许可。

## 单条录入衔接中的来源读取与导航缺口（2026-09-08）

**现象：** 开启工作区鉴权时 JD 请求缺少访问令牌；历史保存时间没有时区；新建或重复提示返回的投递若不在列表缓存中，无法立即打开准备页。

**根因：** JD service 独立调用 fetch 未复用 auth headers；SQLite UTC 时间直接序列化为无时区字符串；详情导航只从列表缓存解析身份。

**修复：** JD 请求使用现有 authHeaders，历史时间按 RFC3339 标记 UTC；新增入口在导航前纳入返回身份并保留后续列表重取。关闭表单后的旧异步回调增加代际检查，避免意外导航。

**教训：** 创建成功、列表刷新和资料读取是三个独立结果，必须分别验证恢复路径。来源字段不因此变成可访问的网址；令牌只用于本地 API，不写入草稿或来源。

## 用户修改确认参数后，模型建议改回旧值（2026-09-07）

**状态：已实现确定性回执边界；验证与限制见 [P0 记录](../artifacts/2026-09-08-harness-p0/verification.md)。**

**现象：** 用户把签字费从10000改为8000、远程办公从两天改为一天并批准后，模型仍可能把新值解释为保存错误，建议恢复原请求。

**教训：** 需要确定性保证的确认边界必须由可信业务事实控制，不能依赖模型措辞。业务提交成功与回执交付必须分别恢复，不能直接返回未保存的成功字符串。停止自动续答仅适用于本次成功编辑确认；模型文字二次确认、虚构按钮和多入口展示属于独立问题。

## 日程时区偏移（2026-09-07）

**现象：** Pilot确认15:00后，日历显示23:00；带非零offset的API输入亦受影响。

**根因：** SQLite DateTime丢弃offset而保留wall time；仓库未先换算UTC，API回读又给无时区值补UTC。页面通常提交Z时间，因而掩盖了另一入口的问题。

**修复：** 日程仓库普通/绑定/scoped创建和更新统一将scheduled_at、remind_at换算成UTC再写入；naive保留既有UTC含义，参数原文、事务所有权和Provider契约不变。未对无法恢复原始offset的历史行做批量迁移。

**验证边界：** 新增东八区、负offset、跨日、UTC、naive、提醒和回滚测试；API覆盖创建/更新/列表回读。复现用例先在旧实现出现8个偏移失败。模型虚构按钮或误解用户修订是独立回复质量问题，不属于本条修复。

**教训：** 以存储边界保存同一时刻，不只在显示层做时区转换；同一功能必须覆盖页面与工具输入的不同时间编码。

## 多标签页覆盖待恢复提交（2026-09-08）

**现象：** 两个标签页同时更新待恢复提交时，后写入的数组可能覆盖另一个请求，导致恢复入口丢失；不会因此自动重复执行请求。

**根因：** `chatSubmission.ts` 将所有请求存放在一个 localStorage 数组，增删和接纳更新均先读后写。localStorage 单次写入原子性不能保证整个读改写过程原子。

**修复：** 按 request ID 独立保存恢复身份，每次只修改对应键。旧数组保持只读；对应独立记录覆盖旧值，删除旧请求用无正文标记抑制旧入口。快照按 ID 排序以保持 React 订阅稳定；存储不可用时保留本标签页内存恢复。

**验证：** 在第一个标签页写入前确定性插入第二个标签页新增请求，覆盖新增、标记接纳、删除请求及按会话删除四种交错；旧实现全部丢失第二个请求，修复后均保留。另覆盖旧数据重新加载、跨标签事件订阅、稳定快照和存储写入失败。

**教训：** 多标签页共享的集合不要通过全量读改写维护独立请求；请求幂等执行与客户端恢复入口持久化需要分别验证。

**剩余边界：** 本修复隔离不同 request ID 的写入。同一 ID 在两个标签页并发接纳和遗忘仍可能留下多余恢复入口；这是只读恢复提示，不会触发自动执行。暂不为此引入永久终态标记或异步事务存储。

## PowerShell 门禁在原生命令失败后仍显示通过（2026-09-10）

**现象：** pytest、前端构建、`oc smoke` 或可选子门禁返回非零退出码后，PowerShell 发布入口仍继续执行并显示 `Release gate passed`；发布入口与 local smoke 还会重复构建前端。

**根因：** `$ErrorActionPreference = "Stop"` 不会自动把 Windows PowerShell 原生命令的非零退出码变成终止错误；父脚本也未检查子 PowerShell 的退出码。local smoke 无复用本轮成功构建的显式参数。

**修复：** 发布、local smoke、安装及 Docker PowerShell 入口逐项检查原生退出码并终止；Shell/PowerShell local smoke 默认构建，发布入口只在构建成功后传 `--skip-build` / `-SkipBuild`，跳过时仍要求存在 `web/dist/index.html`。真实 CLI 启动、HTTP、HITL 与业务 smoke 覆盖保留。

**验证方式：** 隔离命令夹具执行实际门禁脚本，注入各步骤非零退出码，验证停止后续步骤、父入口非零且无成功提示；同时覆盖单次构建、独立 smoke 默认构建、缺产物与参数传递。修复前已复现失败仍显示通过和双构建。

**教训：** 成功日志不是成功证据；每层脚本必须传播失败。构建产物存在不等于匹配当前代码，复用需要同一成功构建的上下文。

**同轮走查补充：** PowerShell local smoke 原先只停止启动器，真实通过或启动超时后均可留下 uv/oc/Python 子进程。改为清理本次启动器的进程树、限时等待退出，始终恢复调用者数据目录环境；清理失败不显示通过。回归覆盖成功/失败后的清理和清理本身失败。首次新虚拟环境冷启动曾在依赖字节码写入时超时，保留失败记录，不调整健康检查超时。

## 获批基线复用时比较了未获批的 A 分组（2026-10-13）

**现象：** 一个 A/B 运行晋升的是 candidate 分组。发布预检允许复用同一运行时，相对门禁仍因 run_id 相同选择原 baseline 分组，可能将候选与自身的复用错误报告为修复或不可比较。

**根因：** 通用比较器的 same-run 默认语义是 A 对 B，正式门禁未传入获批分组身份。

**修复：** 通用比较器保留直接 A/B 比较的默认行为；正式门禁的原始及人工复核比较显式使用获批运行的 candidate 分组，并在报告中记录双方分组。不存在的分组拒绝比较。

**验证：** 合成回归覆盖 A 失败/B 通过的获批复用、candidate-only 复用、预检到执行与回执重校验，以及原直接 A/B 的 fixed 判定。合成审批夹具不表示实际维护者批准。

**教训：** 实验运行身份与获批结果分组身份应同时绑定；同一 run_id 不能替代晋升分组的明确选择。

## Windows 平台元数据初始化被评估隔离层误判（2026-10-13）

**现象：** 冻结的确定性 E08 运行记录到 `platform.machine → uname → win32_ver → _syscmd_ver` 的进程尝试，导致 authorized_deltas 失败。该路径是 Windows 在 WMI 不可用时读取系统版本的本地 `ver` 回退。

**根因：** 中性启动器先安装进程审计围栏，后续依赖首次读取平台信息时才填充标准库缓存，可信环境初始化因此被归为产品进程越界。

**修复：** 在安装围栏前预热 `platform.uname()`。安装后的进程、网络及存储限制保持原判定；历史失败记录不改写。

**验证：** Windows 新进程回归在公开 win32_ver 接缝注入相同的 subprocess.Popen 审计事件，证明元数据预热不被拦截，而安装围栏后的 os.system 仍被拒绝。37 项 core integrity 测试、Ruff 与 bootstrap mypy 通过；此回归不依赖实际 WMI 或执行 shell。

**教训：** 隔离初始化须区分可信平台准备与产品执行，不能通过放宽产品进程权限消除环境误判。

## 超时写入竞争让迟到清理把未知结果改为失败（2026-10-13）

**现象：** E08 的主业务修改已经提交，真实运行 deadline 将任务公开为 result_unknown；释放迟到结果后，公开状态可能变为 failed。原始冻结观察保留，不能因为没有额外业务 DML 就把该状态变化判为通过。

**根因：** 超时控制先以零等待 try_finish 尝试写 interrupted，SQLite 忙锁可使其未成功。Durable control 的 finally 只按较长租约判断终态，忽略已发生的 TIMED_OUT，随后将仍为 running 的持久行写成 failed。只在等待数据库锁前采样状态仍有竞争窗口。

**修复：** 仓库取得写锁并核对同 owner/Turn/generation、仍有效的 running 行后才解析终态。控制器用短 CAS 领取完成权；超时先赢时始终选择 result_unknown，完成先赢时 watchdog 不再广播超时未知。数据库锁等待不持有控制器锁；超时初次探测仍为零等待。已结束或过期的行、恢复 scope 和业务提交围栏沿用原约束，worker 自身的超时异常仍收敛到 unknown。

**验证：** 三种迟到终态及 watchdog 完成竞争分别在旧实现复现失败；70 项 control、manager、event-sink 回归通过，含真实 SQLite 写锁竞争、首个探测未成功、正常 completed/failed、旧终态不覆盖和物理 worker 异常收敛。Ruff、相关四模块及全库 228 文件 mypy 通过。端到端及完整门禁结果见本轮冻结验收记录。

**教训：** 较长的执行租约不能替代较短的产品 deadline；终态决定必须与超时控制有明确先后关系，且不得让超时等待业务数据库锁。

## 2026-10-19：故事撤销在相同时间戳下误判来源链不可读

**现象：** 完整本地门禁中，确认故事后归档，再撤销原操作返回 `503 operation_result_unknown`，未得到预期的 `interview_story_undo_stale`。封存库中确认和归档具有完全相同的微秒时间戳；原始失败及数据库另存保留。

**根因：** 后续生命周期用 `confirmed_at > parent_time` 选取，漏掉同一时刻但修订号更大的事件；历史前缀又用 `<=` 混入同一时刻但逻辑上更晚的事件。同时间戳排序依赖事件类别和字符串 ID，也不能表达归档、恢复、追加版本的实际先后。

**修复：** 时间戳相等时用故事 CAS 修订号划分历史前缀和后续事件，并按因果修订顺序重放。修订号只用于选择和排序，原有完整来源、摘要、时间、状态及所有者校验继续执行；缺失、篡改或不连续的证明仍失败关闭。旧格式手动记录按已知修订位置的缺口恢复排序提示，并通过原请求指纹验证重建的 CAS，保留可证明的旧记录。没有修改确认机制或超时阈值。

**验证：** 在旧实现确定性复现相同时间戳的原失败，以及含十次归档／恢复、追加版本的两个顺序边界；回归同时覆盖同时间戳下的来源篡改。实际命令、结果及完整门禁状态见本轮追加的冻结验收记录。

**教训：** 墙钟时间不提供严格事件顺序；相同时间戳需要领域修订序列来确定因果关系，排序提示不能替代逐项完整性验证。

## 2026-10-30：离线 real-ai 控制器的预留与终态归档边界

**影响**：新控制器离线资格验证；没有真实 Provider/Judge 请求或总账修改。

### 现象与根因

- 新账本原型只在最终 verify 核对前缀，外部截断后仍可能返回下次 allowance。
- generator 在首次 next 前 close 不执行 finally，留下 SDK 原始流未关闭。
- Windows 标准流包装器关闭不保证 OS fd 立即 EOF；仅等待 EOF 的终态协议
  使子读取线程在解释器退出时仍持有 stdin 缓冲锁。
- MockTransport 的已缓存 Response 不再迭代原 stream，普通 tee 因而遗留
  一个 active body；不能把它误当作真实网络流已完整归档。
- 仅清理 proxy 环境变量不能清理 Windows 注册表代理；隔离 loopback 被
  网络围栏正确阻断。这个新引导失败不解释历史其他连接超时。

### 修复与约束

保持账本 fd/身份并逐次核对前缀；显式可关闭的流对象；请求绑定 finished
ACK 后等待全树和真实 EOF；缓存/流式 body 分层归档；隔离 HTTPX 明确
trust_env=false。失败原样保留，新版本资格测试使用假账户、真实 SDK、
MockTransport 和 owned loopback。实现见 [ADR-0014](architecture/decisions/0014-meter-official-real-ai-verification.md)。

### 教训

金额守恒、控制终态、物理发送、模型结果和原始归档必须分别举证；
模拟修复通过不能替代正式评测、真实模型或发布门禁。
