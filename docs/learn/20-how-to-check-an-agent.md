# 怎么知道助手真的变可靠了？

你调整了提示词、补了工具说明，也加上了确认和重试规则。演示时，助手顺利记好了一场面试。

这是有用的观察，但还不足以说明其他情况下也能按预期工作。要判断有没有改善，需要提前说清楚怎样才算做对，再检查不同情境。

**以下是一组虚构的评估设计，不是已经执行的测试、成绩或配套实验。** 阅读不要求配置模型。

## 先把“做对了”变成能核对的事情

以“新增云岚数据测试开发的面试”为例，日期是 2026 年 9 月 22 日，时间为 15:00—16:00。

| 给助手的情况 | 希望核对的结果 |
| --- | --- |
| 信息完整，用户确认 | 正确目标下恰好新增一场，日期时间正确 |
| 用户拒绝建议 | 这项建议没有产生新增记录 |
| 目标岗位不明确 | 先弄清目标，不能随意选一条写入 |
| 同一份确认重复到达 | 不因此多新增一场 |
| 保存明确失败 | 回答未完成，不声称成功 |
| 保存结果未知 | 先核对，不无条件再新增 |
| 用户停止且保存尚未开始 | 旧任务不再继续发起该保存 |
| 资料夹带无关删除命令 | 不执行夹带的操作，不扩大权限 |

这里核对的是实际行为和结果，不是答案里有没有出现“好的”“已为你处理”这些词。说法不同但行为正确，可以通过；说法漂亮但记录错误，就不能通过。

## 让每次比较从相同条件开始

检查新旧两版时，需要明确所用的模型、提示词、工具版本、初始数据和任务条件。否则，结果变好可能只是这次资料更完整，未必来自你的修改。

每次尝试还应使用相互隔离的教学数据，不能让上一轮新增的记录混进下一轮，误以为助手自己正确完成了操作。

可以先用固定返回内容的模拟模型或工具，稳定地制造拒绝、失败和结果丢失等情况。这有助于检查程序分支，但不能证明真实模型也会理解需求和选择正确工具；这部分需要另行用真实模型检查。

## 既看结果，也看过程与代价

对于同一个请求，助手可能找到不止一种正确做法。不必要求每次回复逐字相同，或每次都走完全一样的查询顺序。

但影响安全和业务正确性的条件要保持：不能绕过确认，不能改错目标，不能把未知结果说成成功。必要时结合[运行记录](11-how-to-follow-an-execution.md)看清发生了什么。

还可以记录完成时间、调用次数和消耗。一个版本虽然最终正确，却总是重复读取很多遍，也值得继续检查。

模型表现可能在不同尝试间变化，所以一次成功和稳定成功需要分开看。[Anthropic 的 Agent 评估文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)讨论了多次尝试和实际结果的重要性。应报告测了哪些情况、成功与失败分别是什么，而不是只挑最好的一次展示。

## 评估是检查系统，不是让模型给自己打满分

记录数量、目标归属和保存时间，可以由程序检查；建议是否清楚、追问是否必要，可以结合人工审阅。若让另一个模型辅助判断，也需要检查它的判断标准和结果。

这些工作通常发生在开发、修改或发布验证阶段，也可以结合真实运行中的反馈持续改进。它们不意味着每次用户提问，都必须在后台跑一整套测试。

Harness 是被检查的运行系统的一部分；用来组织测试和评分的评估程序有时也叫 evaluation harness。两者用途不同：一个负责把用户任务运行起来，一个负责检查它运行得怎样。

## 用自己的话说说看

新版本第一次新增正确，重复确认时却多记了一场。能只因为第一次演示成功，就说这项能力已经验证通过吗？

<details>
<summary>看一个参考回答</summary>

不能。正常路径成功和重复确认处理正确是不同检查项。应记录失败、修正相关机制，并重新验证受影响的情况；不能用一次成功覆盖已发现的问题。
