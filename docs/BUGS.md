## 当前记录

## 图片消息合并后的流式与快捷发送回归（2026-10-23）

**现象：** 图片分支与主线整合时，旧同步测试替身不再覆盖受控异步流；图片异常重复包装会丢失超时与 HTTP 分类，快捷能力还可能误带图片草稿。

**根因：** 图片传输和主线中断机制分别改动相同客户端边界；正文发送与快捷能力复用了携图回调。

**修复：** 私密图片包装接入可中断异步流并保留关闭及控制异常，复用安全诊断；无图片请求继续走主线范围校验与失败语义。快捷能力独立发送，重试只展示原请求图片，并保留未发送草稿。

**教训：** 合并不能只消除文本冲突；以本地 HTTP 覆盖带图停止，分别验证正文、快捷操作、拒绝与重试的草稿归属。

## 图片草稿导致窗口切换时控制器引用变化（2026-10-13）

**现象：** 接入 Haru 图片入口时，既有 surface 切换回归发现，仅展开 Pilot 就会改变共享 controller 的对象引用。

**根因：** `useChatImageDrafts` 每次渲染都创建新的 action 和返回对象，使外层 controller 的 memo 失效，即使草稿没有变化。

**修复：** 稳定草稿操作函数，并只在草稿或操作实际变化时生成新的返回对象；上传完成及移除仍通过当前草稿 ref 更新。

**教训：** controller 的子状态 hook 也需要保持无状态变化时的引用稳定。保留窗口切换与上传后移除的既有行为回归。

## Haru 图片预览的 Escape 同时关闭对话（2026-10-13）

**现象：** 从 Haru 放大图片后按 Escape，图片预览与轻量对话一起消失。

**根因：** 图片预览通过 portal 展示，焦点仍可能在 Haru；外层对话的 Escape 处理没有识别图片预览状态。

**修复：** Haru 以图片身份控制当前预览的可见性，Escape 先关闭活动预览；没有活动预览时才关闭 Haru。仅忽略外层按键不足以解决焦点仍在 Haru 的场景。

**教训：** modeless 对话上的 portal 预览需要明确退出顺序，不能仅根据 DOM 层级判断键盘事件归属。
## 共享候选失效请求与过期提醒复活（2026-10-21）

**现象：** 候选读取途中来源变化后，旧请求仍可落盘为新鲜缓存；当前候选到期消失时，已发布的普通提醒又进入当前主动任务列表。

**根因：** invalidateQueries 的非取消分支合并了旧请求，且成功提醒只按“是否已有候选”去重，未区分历史与当前事实。

**修复：** 显式取消旧读取后重新失效，复核期间不使用缓存候选；已发布普通提醒仅进入默认折叠历史。保留失败、未知、草稿和取消状态，不删除任务记录。真实 QueryClient 覆盖首轮/已有缓存的并发失效以及双消费者连续来源更新。

**教训：** 只读结果同样需要来源失效围栏；任务成功是历史事实，不代表其内容仍是当前待办。

## CLI 关联分析绕过岗位版本身份（2026-10-21）

**现象：** 真实 CLI 的 `analyze --app … --jd …` 与 `resume match --app … --jd …` 可以把任意文本关联到已有投递，落库 `jd_version_id=NULL`；对应 HTTP 输入已拒绝此用法。临时 SQLite + stub 模型、CLI/HTTP 同矩阵先复现 2 个 CLI 失败用例，HTTP 对照通过。

**根因：** CLI 与 API 分别维护模型编排，CLI 调用无版本保护的普通 create；HTTP 已实现的来源冻结和模型后 CAS 没有进入共用 workflow。

**修复：** 两个入口复用有限分析/匹配/出题 workflow。关联分析必须显式指定当前版本，保存真实原文及版本身份，并继续通过事务内 CAS 提交。旧 CLI 输入给迁移提示，不静默替换文本；独立文本分析保持可用。提示词、JSON 边界、题目去重及 safe error 分类共享。

**教训：** 共享能力应按业务不变量合并，不能让较完整入口回退到较弱旧实现。跨入口回归覆盖初始陈旧版本、生成中来源更新、非法/重复键/超长输出和原始 Provider 错误脱敏，而非只验证无关联成功路径。

## 统一提醒候选遗漏普通日程卡片（2026-10-21）

**现象：** 候选统一后，72 小时内的笔试、Offer 进展和自定义日程不再出现在今日待办。

**根因：** 原前端展示覆盖所有日程类型，迁移时误把主动发送的 interview/deadline 白名单当作完整展示范围。

**修复：** 补只读 event_upcoming 候选，保留稳定事件身份、来源版本和 todo 资格；其投递窗口为空，不扩大发送 allowlist 或发现逻辑。共享固定时钟样例覆盖三类日程的 24/72 小时、到期、done/cancelled 和来源失效，确认全部主动开关开启仍不会创建任务。

**教训：** 统一业务事实不等于统一权限范围；迁移要分别核对原展示表面和原执行许可，不能用其中一者替代另一者。

## 布局验收与导航覆盖测试共享 Vite 缓存（2026-10-19）

**现象：** 完整 Windows run 39299451507 的首个 `900x689-0-failure` case 在 15 秒 readiness 等待超时，截图为纯背景；其余 123 项通过。原 run 未保存 DOM、console 或 network，因此原空白根因仍未知，不能归因于 runner 负载或当作布局断言失败。

**已证实耦合：** `coverage-model.test.mjs` 使用生产 web root 的默认缓存，虽配置 `noDiscovery=true/include=[]`，React 插件仍加入四个 React 依赖。该部分缓存与后续布局服务有相同配置哈希，首次加载再发现依赖并触发 full reload。独立对照 [run 39304127954](https://github.com/offercontext/offerPilot/actions/runs/39304127954) 的 7 项真实前置测试通过，捕获了四项到十四项缓存及 reload；之后冷、热页面都正常恢复。旧成功完整 run 也有相同 reload，故这一机制尚不能证明原超时根因。

**改进：** 覆盖测试使用独占临时 Vite cache，并以嵌套 finally 保证关闭异常时也清理。列表布局 case 在失败时保存脱敏 DOM 结构、readiness 状态及限量分类 console/pageerror/network/navigation/reload 事件；采集失败不覆盖原失败。15 秒、原断言和 case 范围保持不变，无自动重试或延时。

**验证边界：** 独立候选验证覆盖缓存不再污染布局服务，以及故意不 ready 的浏览器负对照必须保留现场并非零退出；定向通过不能替代完整发布验收，也不将本记录升级为原空白问题已根治。

**教训：** 测试 helper 的 Vite 缓存应明确隔离；HTTP 200 只表示入口可访问。初始化超时需要保留实际页面状态与错误证据，不应靠延长 timeout 掩盖。


## Windows 冻结依赖来源迁移候选（2026-10-19）

**现象：** 完整 Windows run 39299451507 的 shard 9 在测试前下载 TUNA 的 httpcore 1.0.9，六次重试后仍于 89.7 秒发生 TCP timeout；增加重试未消除来源连接失败。

**根因：** frozen 锁包含镜像的绝对下载 URL。不能依靠临时 index 覆盖透明回退，也不能把旧 lock/run/attempt 证据作为新来源的验收。

**修复候选：** 对 82 个 registry 条目的全部 2,254 个锁定 wheel/sdist，逐一核对官方 PyPI 精确版本 JSON 的 filename、类型、SHA256 与 size。仅将 2,252 个 artifact URL、81 个 package registry 及四个必要的 rpds-py 依赖 registry 引用改为官方来源；包版本、依赖图、marker、artifact hash/size/upload-time 和其他字段不变。候选须以新锁身份完成独立冷缓存安装验证，之后再决定完整验收恢复。

**已有风险：** charset-normalizer 3.4.8 原锁即为同版同 hash。其官方 [3.4.9 release](https://github.com/jawah/charset_normalizer/releases/tag/3.4.9) 说明 3.4.8 因 fallback 解码回归而撤回；本次不升级，也不把功能缺陷称为安全漏洞。根项目 hatchling 构建要求原本未固定版本、未收入 uv.lock，其传递/动态构建依赖仍是既有可复现性缺口；无额外 index 覆盖时，新旧锁的构建解析均使用官方默认源。

**教训：** artifact 摘要保持不变不等于 lockfile 身份不变。所有平台的来源等价证据、实际 Windows 安装和完整产品验收各有边界，不能互相替代；未验证前不得宣称恢复完成。

## Windows 冻结依赖下载在测试前连接超时（2026-10-19）

**现象：** Windows run 39246366093 的 shard 9 在 `uv sync --frozen` 下载 attrs 26.1.0 时，三次请求重试后于 44.4 秒报 TCP connect deadline；pytest 尚未执行，未产生 shard 结果。

**根因：** `uv.lock` 固定了 TUNA registry 与 wheel 绝对 URL；该次连接失败耗尽 uv 默认的三次请求重试。单个失败不能证明镜像整体宕机。`--frozen` 同样锁定 URL，额外 index 参数不能透明替换该下载来源。

**修复：** 四处 Python 安装独立成 step，仅安装时设六次 HTTP 请求重试，并显式保留十秒连接、三十秒读取超时。uv 版本、依赖锁、失败检查、产品测试及 manifest/run/attempt 身份校验保持原样；不重试整个测试或 workflow。保留原安装 transcript。独立诊断验证后仅对四个安装 step 增加五分钟上限，不包含 npm 或 pytest。

**验证边界：** 独立 Windows 诊断 [run 39260306504](https://github.com/offercontext/offerPilot/actions/runs/39260306504) 使用 uv 0.12.19，空缓存完整 frozen sync 为 10.157 秒，六组 loopback 对照全通过；永久 503 七次请求后于 69.188 秒失败。五分钟上限有本次观测裕量，不是未来网络时延保证。

**教训：** 网络恢复应限于传输层并有次数边界。404、错 hash、构建错误继续失败；官方源迁移须审查锁文件来源与哈希变化，不能临时改锁后冒充原验收身份。独立下载诊断不能替代完整发布验收。

## 消息清理回归误把其他组件的定时器计为泄漏（2026-10-17）

**现象：** PR #36 第五候选的完整 Windows 前端测试中，新增消息清理回归确认 portal 已消失，但全局 fake timer 数量仍为 1；原 14 项投递业务场景通过。

**根因：** 全局计数无法证明剩余资源属于消息。离线控制真实 ResizeObserver polyfill 的已断开 observer 尾回调跨越时钟切换，可确定性重现独立 jsdom animation-frame interval 留存、消息自身 expiry 已释放的相同症状；未取得 Windows 失败现场的 timer callback 栈，不能断言该次剩余资源必为此 interval。

**修复：** 回归只追踪本次真实 message.open 期间唯一注册的 expiry 句柄，检查销毁前未取消、销毁后精确取消、portal 消失以及推进原定时器后专属 onClose 不触发。保留普通路径并加入真实 ResizeObserver 尾回调交错；独立 frame 由自身生命周期释放，失败收尾也只取消该 fixture 自有 frame。完整表单文件加入既有 installer 早期聚焦门禁，最终全量不减少。

**验证边界：** 故意阻止该 expiry 句柄的真实 clear 后，即使 spy 记录和 portal 检查通过，专属 onClose 仍触发并使新断言失败。此负例证明资源断言有效，不代表新的 Windows 合并候选已验收。

**教训：** 清理检查应验证资源归属与实际到期行为，不能将第三方组件的独立计时器混为消息泄漏，也不能清空全部 timers 掩盖残留。

## 严格离线升级测试误拦 Windows 内部 socketpair（2026-10-16）

**现象：** PR #36 旧 Windows 分片的两个桌面邮件组合测试在 TestClient 启动前失败，栈停在 asyncio Proactor 创建内部 socketpair 的 connect。集中扫描还发现 master 既有邮件升级测试使用相同的全禁 connect 方式。

**根因：** Windows 的标准库 socketpair fallback 通过自有临时 loopback listener 配对；严格离线测试把它与任意业务网络连接一并拦截。Linux 强制真实标准库 fallback 可复现相同失败栈。

**修复：** 仅测试 helper 识别捕获的标准库函数对象、直接调用 code/globals、自有 socket/listener 与精确临时目的地，再交给此前已安装的 connect 防护。不能证明身份时拒绝，任意 loopback、外网、凭据及模型入口继续禁止，并补 connect_ex/sendto 拒绝。两份升级测试和 helper 负例加入现有 Windows installer 聚焦门禁，完整分片覆盖保留。

**教训：** 离线防护应区分可证明归属的运行时内部通信，不能为了跨平台兼容放行所有 localhost，也不能只靠 Linux 默认 socketpair 验证 Windows 路径。

## 邮件状态读取组合不同数据库快照（2026-10-16）

**现象：** PR #36 的旧 Windows 全量分片中，邮件预算回归读到 used=99 而预期 100。日志未记录完整 run 状态，不能唯一还原该次失败；独立事件屏障复现确认可返回 completed 与旧预算 99，而持久数据库已是 100。

**根因：** master 既有 status 依次查询 connection 与最新 run，SQLite legacy 模式不会为 SELECT 自动开启真实读事务，worker 可在两次查询之间提交。预算准入、attempt 与 used 增量仍在原 BEGIN IMMEDIATE 写事务内，未发现预算丢更新或突破上限的证据。

**修复：** status 用短 deferred BEGIN 与 finally rollback 固定读快照，先物化普通 dict，再退出事务调用 folders/catalog。保留原测试等待、预算断言、全局 journal 与超时；新增允许旧 running 快照但拒绝 completed+旧预算的确定性回归，以及默认 journal 下外部回调写入和异常释放检查。

**验证边界：** WAL 仅用于临时测试数据库让屏障内 writer 能提交；产品默认 DELETE journal 的短共享读锁仍可能短暂推迟 writer commit，不宣称完全无阻塞。

**教训：** 轮询终态与关联计数必须来自同一数据库快照；一次重跑通过不能排除竞态，也不能用增加 sleep 或削弱断言代替一致性修复。

## 离线启动防护测试未记录 Windows venv launcher（2026-10-16）

**现象：** PR #36 的 Windows cleanup 回归为 44 通过、1 失败，唯一 early guard 记录的 ppid 与 pytest PID 不同。

**根因：** 旧测试使用 subprocess.run，未保留本次受控 launcher PID，只允许直接解释器，未覆盖 Windows venv 的一次转发。

**修复：** 测试用 Popen 持有 launcher，子输出 pid/ppid 与 guard 记录一致；直启必须指向 pytest，仅 Windows 真实 venv 允许指向本次 launcher 的单跳。保留外网 fail-closed 断言和 20 秒期限，不修改产品防护。

**验证边界：** Linux 参数化拒绝分支不能替代 Windows 真实进程验证，仍以更新候选 CI 为准。

**教训：** 平台判定不能替代本次进程归属证据；不能接受任意父 PID 或任意后代。

## 邮件 Windows 原生锁门禁漏装启动防护依赖（2026-10-16）

**现象：** 集成候选 PR #36 的邮件合成验收通过后，Windows 原生锁 job 在收集前导入 httpx 失败，4 项锁测试尚未执行。

**根因：** 该独立 job 原先仅安装 pytest；合入的 pyproject 通过 `-p tests._offline_network_guard` 提前加载离线网络防护，而 `--noconftest` 不会禁用该插件。防护同时需要 httpx、requests、starlette 和 aiohttp，不能只补第一个缺失库。

**修复：** 复用邮件 workflow 原有 uv 0.8.22，通过 `uv sync --frozen` 安装完整锁定依赖，再以 `uv run --frozen pytest --noconftest` 执行原文件。保留启动防护、原 4 项测试及断言，不修改依赖锁或禁用插件；新增 active CI 配置回归。

**验证边界：** Linux 本地检查不能替代 Windows 原生锁执行；Windows 预期执行 3 项并按原标记跳过 1 项 POSIX 专用用例。

**教训：** 独立测试环境也受仓库启动插件约束；精简安装必须涵盖插件依赖，不能靠绕过安全防护使门禁变绿。

## 授权源码审计重复展开与跨审计缓存失效（2026-10-16）

## 展示刷新失败遮住最新持久消息（2026-09-08）

**现象：** Pilot / Haru 成功加载一次展示后，后续展示请求失败，已保存的新问题和回复仍被旧快照遮住。

**验证：** 新增回归先复现失败，再验证持久消息回退、刷新恢复和旧请求拒绝隔离；相关前端 47 项通过。迁移基线为新仓库 `origin/master`，顺序迁入 `608272c → bda0ef7 → ecaa2b5`，对应 `a0e9519f → 478568b3 → 64c988e8`。

**教训：** 快照的加载中保留策略必须有失败出口；首轮加载失败测试不能替代已有缓存后的刷新失败测试。

## 未知录入另建后重开丢失恢复入口（2026-09-08）

**现象：** 未知提交选择承担风险另建后，关闭重开表单不再显示旧提交；新增恢复存储也未与既有隐私审计契约对齐。

## 单条录入衔接中的来源读取与导航缺口（2026-09-08）

**现象：** 开启工作区鉴权时 JD 请求缺少访问令牌；历史保存时间没有时区；新建或重复提示返回的投递若不在列表缓存中，无法立即打开准备页。

**根因：** JD service 独立调用 fetch 未复用 auth headers；SQLite UTC 时间直接序列化为无时区字符串；详情导航只从列表缓存解析身份。

**修复：** JD 请求使用现有 authHeaders，历史时间按 RFC3339 标记 UTC；新增入口在导航前纳入返回身份并保留后续列表重取。关闭表单后的旧异步回调增加代际检查，避免意外导航。

**教训：** 创建成功、列表刷新和资料读取是三个独立结果，必须分别验证恢复路径。来源字段不因此变成可访问的网址；令牌只用于本地 API，不写入草稿或来源。

## 用户修改确认参数后，模型建议改回旧值（2026-09-07）

**状态：已实现确定性回执边界；验证与限制见 [P0 记录](../artifacts/2026-09-08-harness-p0/verification.md)。**

**现象：** 用户把签字费从10000改为8000、远程办公从两天改为一天并批准后，模型仍可能把新值解释为保存错误，建议恢复原请求。

**根因：** 续答已有实际批准参数和工具结果，但缺少“差异来自用户主动修订”的明确语义；原始用户请求仍在上下文中，模型可能错误地把旧请求当作最终意图。

**修复：** 用户合法修改参数且规范化后与原提案不同、Ledger 可靠证明提交成功时，结束本次确认后的模型续答。回执从原终态结果构造，与 ToolMessage 原子保存；策略绑定原操作、请求指纹与结果摘要，重启恢复和重复确认不再进入模型。原提案、HITL、Undo 和独立新请求保持可用；等价编辑与失败沿用原分支。决定见 [ADR-0006](architecture/decisions/0006-edited-confirmation-receipts.md)。

**实际验收：** 之前两版提示词各有一次真实样本反向，最严重样本生成恢复旧值的 Pending。本次可控测试先在旧代码证明额外模型调用，再验证成功编辑后的零调用与独立进程恢复。真实模型固定两个隔离 Offer：初轮仅文字确认，在原对话各补一次明确确认后均进入系统 Pending；编辑为 8000/一天后，sync/SSE 和交叉重放通过，总调用 6 次（上限 8），确认阶段零调用。首轮结果全部保留，不隐去未进入 Pending 的情况。

**教训：** 需要确定性保证的确认边界必须由可信业务事实控制，不能依赖模型措辞。业务提交成功与回执交付必须分别恢复，不能直接返回未保存的成功字符串。停止自动续答仅适用于本次成功编辑确认；模型文字二次确认、虚构按钮和多入口展示属于独立问题。

## 日程时区偏移（2026-09-07）

**现象：** Pilot确认15:00后，日历显示23:00；带非零offset的API输入亦受影响。

## 多标签页覆盖待恢复提交（2026-09-08）

**现象：** 两个标签页同时更新待恢复提交时，后写入的数组可能覆盖另一个请求，导致恢复入口丢失；不会因此自动重复执行请求。

**根因：** `chatSubmission.ts` 将所有请求存放在一个 localStorage 数组，增删和接纳更新均先读后写。localStorage 单次写入原子性不能保证整个读改写过程原子。

**修复：** 按 request ID 独立保存恢复身份，每次只修改对应键。旧数组保持只读；对应独立记录覆盖旧值，删除旧请求用无正文标记抑制旧入口。快照按 ID 排序以保持 React 订阅稳定；存储不可用时保留本标签页内存恢复。

**验证：** 在第一个标签页写入前确定性插入第二个标签页新增请求，覆盖新增、标记接纳、删除请求及按会话删除四种交错；旧实现全部丢失第二个请求，修复后均保留。另覆盖旧数据重新加载、跨标签事件订阅、稳定快照和存储写入失败。

**教训：** 多标签页共享的集合不要通过全量读改写维护独立请求；请求幂等执行与客户端恢复入口持久化需要分别验证。

**剩余边界：** 本修复隔离不同 request ID 的写入。同一 ID 在两个标签页并发接纳和遗忘仍可能留下多余恢复入口；这是只读恢复提示，不会触发自动执行。暂不为此引入永久终态标记或异步事务存储。

## PowerShell 门禁在原生命令失败后仍显示通过（2026-09-10）

**现象：** pytest、前端构建、`oc smoke` 或可选子门禁返回非零退出码后，PowerShell 发布入口仍继续执行并显示 `Release gate passed`；发布入口与 local smoke 还会重复构建前端。

**教训：** 成功日志不是成功证据；每层脚本必须传播失败。构建产物存在不等于匹配当前代码，复用需要同一成功构建的上下文。

**同轮走查补充：** PowerShell local smoke 原先只停止启动器，真实通过或启动超时后均可留下 uv/oc/Python 子进程。改为清理本次启动器的进程树、限时等待退出，始终恢复调用者数据目录环境；清理失败不显示通过。回归覆盖成功/失败后的清理和清理本身失败。首次新虚拟环境冷启动曾在依赖字节码写入时超时，保留失败记录，不调整健康检查超时。

## 2026-10-15：邮件最终预览的固定后端提醒未切换语言

- 现象：英文界面的最终预览仍可能显示两条中文写入范围/旧提醒清除提示。
- 根因：前端直接显示后端 `warnings`，合成浏览器 fixture 又返回空 warnings，未覆盖真实响应。
- 修复：只在展示边界翻译两条确定的后端固定提示，未知文本逐字保留；fixture 按真实字段合并和提醒契约返回数据。
- 验证：增加双向语言/未知文本保留单测及未编辑提案的 fixture 契约断言；真实浏览器英文审计保留严格中文扫描。
- 教训：API 来源不代表用户内容；固定 UI 提醒应明确识别，测试不能省略正常响应中的提醒。

## 2026-10-19 英文固定宽控件与仪表盘说明截断

- 现象：真实 Chromium 截图中，列表排序、看板状态、题库筛选/搜索与 Pilot 搜索被省略；仪表盘说明剩下不完整单词，计数出现 `1 interviews`。

- 修复：英文控件按文字宽度展开，素材库输入与搜索按钮成组；中英文仪表盘说明完整换行；Pilot 使用简短占位提示并保留完整无障碍名称；英文仪表盘说明换行，单数数量用独立词条上下文。
- 验证：新增浏览器控件裁切断言，截图范围扩到全部导航视图；修复后必须重新截图复核，旧 SHA 的通过结果不等同新代码通过。
- 教训：字典与页面 overflow 断言不能替代逐图可读性复核。

## 2026-10-19 本地化整合后的安装验收辅助测试失配

## 2026-10-19 真实安装截图暴露邮件固定文案与未完成绘制

- 现象：英文邮件设置仍显示后端固定执行位置中文；原生引导弹窗、语言下拉与两次 Haru 收起截图捕获过渡或透明帧，尽管 DOM 状态断言通过。
- 根因：网页 fixture 用英文替换真实后端字段，隐藏遗漏；元素存在/状态变更不等于动画结束或 WebGL 已绘制。
- 修复：只翻译该字段的已知固定值，未知值保留；fixture 恢复后端字段形状；原生截图等待有名弹窗不透明且动画完成、语言下拉关闭，以及连续两帧非空角色像素。
- 验证：补字段与未知内容保留、fixture 契约、弹窗与空帧拒绝测试；实际截图仍须按新 head 同包安装复核。
- 教训：实装截图必须审查像素，不能用 DOM 断言或合成英文响应替代；透明/过渡截图不构成视觉通过证据。

## 2026-10-19 完整 Windows 门禁中的标签契约与 RAF 测试隔离

- 现象：完整分片的确认卡中文标签测试误报 39 字段缺失；另一个包装测试偶发预期新 RAF interval 为 1、实际为 0。

- 修复：标签测试由实时双后端 catalog 提供字段，经 Vite/React 渲染真实 ProposalCard 与词典，校验中文、英文非 fallback、切回恢复及未知用户内容保留；RAF fixture 使用独立真实 jsdom 窗口，并主动加入竞争 RAF，保留所有精确次数、句柄归属、清理与 onClose 断言。
- 验证：标签 4 项通过，故意删除标签/缺失译文均能使新契约失败；恢复原同窗口 RAF 的负对照准确复现 1/0 失败，隔离修复后目标 16 项和 TypeScript 通过。最终完整门禁仍需新 head 重跑，不能用这些定向结果替代。
- 教训：跨层契约应验证真实渲染而非易变的源码排版；测试拥有的时钟/窗口应与前序 UI 任务隔离，不靠固定等待或放宽次数消除抖动。

## 2026-10-21 精简分支的跨平台与浏览器验收失配

- 现象：当前 Windows 门禁仍使用精简前的入口标签；新付费验收 helper 的 Linux 文件耐久性测试被默认 Windows collection 收入；6 个超大模型输出案例在运行前因参数自动 ID 超过 Windows 环境变量长度上限而失败。
