## 当前记录

## 写后超时回归被额外的墙钟截止抢跑（2026-09-10）

**现象：** Chat 流式确认的写后超时回归在全量测试失败，单独重跑通过。现场已有已提交的业务写入，但没有第二次模型调用，也未落库预期的完成消息。

**根因：** 用例本用第二次模型调用抛出超时来验证写后回执，却另设 5 秒 Agent 截止。机器负载变化时，该截止可能先于注入点触发，使测试进入别的超时/恢复分支，而非预设的模型超时场景。

**修复：** 移除该用例专属的 5 秒覆盖，保留产品默认时限；要求确实到达第二次模型调用。完成消息、撤销信息、单次落库和重放一致性的断言不变，产品超时、交付 fence 和持久化逻辑未修改。

**验证：** 以 6 秒写前延迟确定性证明旧用例在同步/流式路径均提前超时且未到注入点；保留有无延迟的参数化回归。另行受控探针在写后模型调用内及模型调用前等待，真实 host 超时均能返回完成回执；相邻执行中超时用例继续负责迟到写入的拒绝语义。

**教训：** 在指定阶段注入故障时，应断言该阶段确实到达，不让额外的短墙钟限制改变被测场景。未取得交付所有权时的保守失败不能被改成无条件成功。

## 浏览器清理异常导致父进程残留和测试无限等待（2026-09-10）

**现象：** 全量测试在 Chromium 延迟就绪回归后停止推进。清理审计显示专用浏览器未退出，PowerShell 已退出；清理该用例专属的残留进程树后，测试恢复推进。

**根因：** `Stop-Tree` 遇到子进程枚举或终止异常便跳出，未继续清理父进程；进程也可能在检查后自行退出。测试启动器的超时处理随后再次调用无时限的 `communicate()`，残留后代持有输出句柄时会无限等待。

**修复：** 清理函数聚合子进程错误但继续回收父进程，只有查询明确返回进程不存在才容忍终止竞争；查询失败不记为已退出，退出超时保留先前清理错误。测试输出使用临时文件，启动及终止后的等待均有明确时限，兜底 kill 异常也保留原始超时诊断，不再等待所有管道写端退出。

**验证：** 确定性覆盖子进程提前退出、枚举或查询失败、终止失败后退出超时，以及清理正常/再次超时/kill 竞争均保留输出并有界返回。

**教训：** 清理过程应尽力回收所有已知资源，再汇总错误；超时后的诊断回收也必须有界。

## 元数据删除门禁遗漏展示入口并误报记录查询（2026-09-10）

**现象：** 全量静态门禁报告撤销展示的反射分类，以及创建回执和面试准备证据查询中的工具名分支。

**根因：** 撤销展示用 `getattr` 探测写操作元数据；另两处是固定 SQL 记录标识谓词，门禁仅按字符串比较识别，误当成运行时工具分派。

**修复：** 撤销展示使用精确的 `WriteOperationMetadataV1` 类型后直接读取字段。静态门禁仅允许两个指定文件/函数中、指定模型/字段/标识的 `select(Model).where(...)` 直接相等谓词，不修改 SQL、权限或持久化逻辑。

**验证：** 新回归先复现两处 SQL 误报，并保留错误文件、函数、字段、模型、工具名、控制流分支和包装调用均被拒绝的反例。

**教训：** 类型化运行时不应反射探测契约；源码门禁应区分固定证据查询与执行分派，例外必须限定语法和所有者。

## 历史夹具字节指纹混用平台换行（2026-09-10）

**现象：** 工具权限基线的夹具身份检查失败，JSON 内容指纹一致，但三个原始字节哈希不同。

**根因：** 历史身份记录使用 Windows CRLF 字节计算哈希，工具管线夹具后来固定为 LF；Agent loop 和 Pilot runtime 夹具还缺少显式换行规则，校验结果依赖检出平台。

**修复：** 为两类遗漏夹具补齐 Git LF 规则，将五项原始字节哈希统一为现有仓库 LF 内容的指纹。夹具 JSON 内容、canonical 指纹、业务契约和原始字节严格比较均保持不变。

**教训：** 固定原始字节指纹时必须同时固定检出换行，不能把本机工作区的默认换行当成跨平台契约。

## 浏览器验收脚本把诊断日志当作 JSON 数据（2026-09-10）

**现象：** Story 浏览器 harness 的七项启动、重试和清理回归在种子初始化阶段失败，`ConvertFrom-Json` 报 LiteLLM 警告不是合法 JSON。

**根因：** `Invoke-IsolatedPython` 将子进程 stdout 和 stderr 合并为函数返回值。调用方将返回值当作 JSON，正常退出时的依赖警告也污染了数据协议。

**修复：** 成功时只返回 stdout，stderr 保留在标准错误通道；非零退出仍将两路输出纳入异常，临时脚本和输出文件的 finally 清理不变。

**验证：** 使用仅依赖 Python 标准库的确定性探针同时输出 JSON 与诊断；旧实现在成功退出时解析失败。覆盖成功可解析、警告保留、非零退出两路诊断和临时文件清理。

**教训：** 机器可解析数据和诊断日志必须使用独立通道，不能依靠依赖库永远不输出警告。

## 提交未知结果测试的故障注入被后台线程消耗（2026-09-10）

**现象：** Story publication commit-unknown 回归在整套测试中偶发未抛预期异常，单独重跑通过。

**根因：** 测试全局替换 `Session.commit` 并将第一次提交设为失败。应用后台线程也使用该方法，可以抢先消耗注入，导致真正受测的 publication 正常提交，根本没有进入预期的恢复分支。

**修复：** 仅统计并注入当前请求线程的提交；其他线程调用原始 commit。领域实现和未知结果的 fail-closed 断言不变。

**验证：** 在 publication 前确定性加入另一线程的空 Session 提交，原注入使 partial/unreadable 用例失败。成功恢复路径同样覆盖提交前/后丢失结果与有无后台提交的四种组合，并断言后台提交不消耗故障计数，避免恢复未被触发时误通过。

**教训：** 并发应用的故障注入应绑定被测请求或事务，不能把进程内第一次同名方法调用当成目标边界。

## 并发撤销在发布与执行之间误判已提交结果（2026-09-10）

**现象：** 全量门禁的二十路 Readiness Signal 撤销竞态失败；先提交的请求已正确完成，后到请求却抛出 `readiness_signal_version_integrity`。

**根因：** 撤销发布与执行分别持有事务锁。另一请求可以在两阶段之间完成同一补偿；执行阶段先按旧 active proof 校验当前领域状态，尚未读取并验证终态账本，就把合法 retracted 版本当成异常 active 漂移。

**修复：** 执行阶段保留锁内 capability 校验，先读取并完整验证账本状态；已提交结果通过既有终态、父操作、指纹和领域快照校验后重放，仅对仍为 proposed 的操作校验待撤销状态。与发布阶段的终态处理顺序保持一致，不重复执行领域写入。独立审查同时发现 Story 归档终态只检查时间范围，补充撤销写入本身保证的 `archived_at == updated_at` 关系，拒绝单字段合法范围内的时间戳篡改。

**验证：** 确定性插入“第一请求发布后、执行前由第二请求提交”的交错，旧实现复现相同错误；修复后仅执行一次、保留两个版本及四条状态转换。另覆盖交错后篡改撤销版本必须被拒绝，并保留二十路并发测试。Story 交错覆盖正常归档及两个时间戳的独立篡改；两个篡改用例在补充校验前均错误重放。

**教训：** 多事务幂等流程中的每个重入点，都应先验证当前持久终态，再按状态选择领域校验；不能用过时的执行前状态拒绝合法终态，也不能仅凭终态标记跳过完整性验证。

## 整合 master 后的历史验收断言失配（2026-09-09）

**现象：** 完整门禁中的 README、JD 实施范围、工具依赖黄金、scoped repository 源码检查和 Offer 对比布局断言失败；前端并行审计偶发超过三十秒预算。

**根因：** README 测试锁定旧日期截图和标题；JD 检查把单次验收的外部临时文件当成全局运行前提；历史二十五工具黄金直接比较新增 `create_offer` 后的二十六工具目录；SQL 外连接的 NULL 占位排除被静态扫描误认成 Python 权限过滤；布局测试没有区分主流程和局部设置抽屉；Vitest 默认并发导致 AST/jsdom 资源争用。

**修复：** 固定 README 当前五张产品截图白名单、仓库内路径及可读性和确认边界；JD 普通回归以临时 Git 仓库验证四种改动状态的越界拒绝，显式外部范围验收仍 fail-closed；历史黄金仅比较原目录投影，当前完整目录继续由独立 current 黄金校验；NULL 占位排除沿用相邻 scoped 查询的 positional 检查，SQL 权限约束不变，并补充状态不匹配与不可用 scope 的区分回归；Offer 对比仍要求工作区主页面，仅允许其明确的局部设置抽屉；测试 worker 上限设为四，不改三十秒预算或测试集合。

**教训：** 区分历史冻结快照、当前产品契约与一次性验收输入；门禁应验证安全语义，不靠过期路径或字段拼写阻止合法演进。不得重写历史黄金或从当前 diff 自动生成批准范围。

## Harness 真实走查中的恢复提示、中文检索与时间歧义（2026-09-09）

**现象：** 已接纳请求断线后能恢复回答，但仍显示重发错误及原输入；自然中文长问题漏召回蓝鲸、紫鹭等来源；面试准备把来源复盘的第二轮混为目标第三轮；主动草稿把 UTC 时间当成本地时间。

**根因：** 终态回读没有按原 request ID 清理失败状态；Knowledge 先截断前十二个词并按旧记录顺序取候选，简单累加中文词命中仍会被通用前缀淹没；准备上下文只有来源轮次，主动来源缺少时区和观察时间。

**修复：** 成功或待确认的原请求回读后清除其错误，仅在输入仍等于原消息时清空；中文短词覆盖整个五百字查询，Note / Evidence 独立按词的文档频次倒数排序并各限二十四项；同一验证快照补充目标面试元数据；草稿来源提供 UTC、本地时间、时区与派发时刻，时区变更纳入来源围栏。

**验证：** 最终相关后端四模块 48 项通过；前端恢复与 Runtime 26 项通过、构建通过；真实断线一次提交自动恢复，原自然问法召回两份订单来源并识别目标第三轮。查询 CTE 显式物化和预计算小写文本，五千条噪声回归在原只读期限内通过。

**教训：** 恢复界面必须以持久化请求身份收敛；召回回归同时覆盖自然问题、短专名、大量通用噪声和后置稀有术语；来源事件、目标事件与用户本地时间应显式区分。HITL、来源失效校验和运行预算保持原边界。

## DeepSeek V4 短草稿与默认思考模式不匹配（2026-09-09）

**现象：** 真实主动草稿调用返回后未通过内容校验，任务安全停留在 `result_unknown`，没有自动重试；普通提醒正常完成。

**根因：** 草稿固定一千零二十四 token 的输出上限，但 DeepSeek V4 默认启用思考模式，两者存在预算兼容风险。现场异常定位到生成结果校验，而非网络超时；未留存失败响应正文，不将预算耗尽表述为已捕获的 provider 终止原因。

**修复：** 仅官方 `api.deepseek.com` 的 V4 Flash / Pro 只读草稿请求显式关闭思考模式；普通聊天、其他主机和其他模型不变。保留单次调用、零重试、无 fallback、原输出与时间上限。

**验证：** 第三个独立合成任务实际完成，返回 `finish_reason=stop`、正文 481 字符、reasoning 零字符；传输仍为一千零二十四 token、零重试、无工具。前两次不确定任务保留，未自动重试，结束后关闭主动总开关。

**教训：** 短预算任务需明确匹配 provider 默认推理行为，不通过增加重试或扩大费用上限掩盖兼容问题。依据：[DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)。

## 确认超时等待仍持锁的后台写入（2026-09-09）

**现象：** 同步和流式确认发生超时后，响应仍可能等待后台 handler 的 SQLite 写事务；测试替身遗漏线程上下文，使迟到写入看似可合法完成。

**根因：** 超时/取消收尾仍使用会等待写锁的终态更新；替身未像生产执行宿主一样复制 Context，使 P3A 写入围栏未传入 worker。

**修复：** 超时/取消仅尝试不等待写锁的终态更新，锁忙时由 lease 到期及对账收敛。连接保持借出直至恢复原 busy_timeout。测试复制真实上下文，并等待 worker 退出后核对无迟到业务写入、ToolMessage、Undo 或后续模型调用；原 Pending/token 保留，显式重试以新 generation 提交一次。

**验证：** 同步/流式慢 handler 共 4 项通过；成功、锁忙、异常三种连接归池路径均恢复原 timeout。已提交写入的超时回执保留独立恢复路径。

**教训：** 超时响应不能依赖被终止 worker 释放业务锁；并发替身必须传递生产使用的授权上下文。

## 旧接口重复保存终态覆盖待确认状态（2026-09-09）

**现象：** 初始对话返回待确认操作，Execution 为 waiting_confirmation，但关联 Turn 被错误标为 completed。

**根因：** Durable control 已按 Pending 状态收敛后，旧 Timeline 写入再次使用传输层的 completed 覆盖 Turn，并可能重新等待数据库写锁。

**修复：** 有 control 时仅由控制器保存终态；无 control 的兼容调用才使用 Timeline writer。终态持久化失败测试改为注入真实控制器的 repository 边界。

**验证：** 同步、流式两项新用例修复前均复现状态不一致；修复后完整接纳围栏模块 5 项通过（61.06 秒）。

**教训：** 终态只能由同一个权威控制边界保存，展示层不能用较粗的 HTTP 成功状态覆盖领域状态。

## 新会话接纳绕过确定性标题规则（2026-09-09）

**现象：** 新 JSON / 流式对话的标题包含原始换行、制表符及后续句子。

**根因：** Durable admission 先创建会话，直接截取原始消息，绕过既有标题规范化函数。

**修复：** API 将既有标题回调注入 Timeline repository，新会话接纳复用首个非空行、空白整理、句界和长度规则；不覆盖已有标题或手工命名。

**验证：** JSON / SSE 标题与手工命名回归通过，纳入 226 项收口回归及独立 CR。

**教训：** 将生命周期入口前移时，一并保留原创建路径的展示契约。

## 深层 JSON 拒绝依赖解释器递归限制（2026-09-09）

**现象：** Python 3.12 可解码 2,000 层 JSON 对象，面试准备请求未在 raw decoder 返回 422。

**根因：** 原实现仅依赖 `json.loads` 抛出 `RecursionError`；不同解释器版本的保护行为不同。

**修复：** 迭代校验增加 32 层容器上限，并保留 surrogate、重复键、非有限数字和解码异常检查。合法请求最多四层容器；超限在 repository / Provider 前拒绝。

**验证：** 31 / 32 层允许解码、33 层拒绝；2,000 层数组和对象均安全返回 422，无 proposal 或模型调用，5 项通过。

**教训：** API 结构边界需显式定义，不能由解释器内部限制代替。

## Windows 门禁错误输出被解码线程丢弃（2026-09-09）

**现象：** PowerShell 失败诊断的 `stderr` 为 `None`，测试拼接输出时抛 `TypeError`。

**根因：** 本地代码页格式化的 PowerShell 错误被当作 UTF-8 解码，`subprocess` 读取线程抛 `UnicodeDecodeError`，原始诊断未返回。

**修复：** 测试先捕获二进制输出，再解码并将不可解码字节显式转义，保留错误码、原有诊断及不可解码内容。

**验证：** Windows 汇总器整组 9 项通过，新增本地编码字节不会丢失的回归。

**教训：** 进程捕获边界不能让文本解码失败吞掉用于判断门禁结果的错误信息。

## 确认超时后误丢交付回执（2026-09-09）

**现象：** 确认写入已提交后，后续模型超时可能误报待确认操作失效；旧流式接口可能只返回前序事件或空 SSE。

**根因：** 固定超时回执直接复用已撤销的 worker scope，交付心跳提交被围栏拒绝并误判为 CAS 丢失。传输层还将 timed_out 下的所有事件过滤，包括 Runtime 已收敛的终态。

**修复：** 同步与流式确认的固定超时回执通过现有控制器的独立终态恢复 scope 收敛，不放宽业务提交围栏。旧 SSE 仅保留已持久化完成回执与不带 Pending 的终态错误，继续过滤迟到文本、未持久化完成及取消后的全部事件。

**验证：** 传输模块 49 项通过；两种传输下 Provider/timeout CAS 及已提交回执 6 项通过；停止和新执行不能被恢复覆盖 2 项通过。传输缺陷先以直接执行与 worker 两种模式复现，再验证修复。

**教训：** 超时撤销 worker 权限与可信终态回执是不同路径；回执必须保持原身份与围栏，传输取消策略不能无差别丢弃已经收敛的事实。

## Runtime 恢复时混用缓存状态与任务身份（2026-09-09）

**现象：** 来源删除后仍可能读取缓存结果；数据库已标记未知的执行可能显示 running；旧任务恢复可能读到同会话后续任务的回复，确认终态也可能带上错误的 Turn 身份。

**根因：** 观察路径过度依赖进程内缓存，恢复按会话取最新消息，确认重放缺少 operation 到 Turn 的绑定检查。容量拒绝发生在接纳持久化之后，启动异常也可能残留 running 记录。

**修复：** 状态、快照和 SSE 重校验来源，数据库已知终态优先；恢复通过持久化 Turn/消息/operation 关联重建结果。确认先校验精确 Turn，再进入拒绝或重放路径。接纳前预留容量，重复请求优先核对原身份，启动失败收敛 lease；进程启动即将旧 epoch 的在途 Runtime 记录标记为未知。

**验证：** 独立审查及 9 项故障回归通过：来源删除、打开中的 SSE 失效、数据库未知状态、错 Turn 拒绝与终态重放、同会话 A/B 驱逐恢复、接纳启动失败、并发重复提交、旧 epoch 围栏。

**教训：** 观察缓存不能覆盖持久化事实；恢复和重放必须保持原任务身份，容量拒绝必须与是否接纳的语义一致。

## Runtime 构造即启动导致空闲线程积累（2026-09-09）

**现象：** 全量测试进程中积累大量空闲 Runtime worker 和 watchdog；仅构造应用也启动线程。

**根因：** manager 构造立即启动固定池，而只构造应用、不进入 lifespan 的调用方没有 shutdown 回调。

**修复：** 构造与容量预约保持无线程；首次有效提交在锁内启动一次固定池，关闭未启动的 manager 安全。启动失败关闭接纳并唤醒已启动线程，不将任务加入无人处理的队列。

**验证：** manager 14 项通过；与真实 API 和接纳围栏组合的 19 项通过，涵盖第二个线程启动失败和首次提交只建一个固定池。

**教训：** 显式启动有工作要消费的资源；应用构造与运行期资源所有权分开，部分启动失败也必须可收敛。

## 知识 Note 修订遗漏旧版本完整性校验（2026-09-09）

**现象：** 损坏 JSON 或已失效的引用可能被修订路径复制；公有读取可能抛出解析错误。

**根因：** 修订只校验编辑命令与版本 CAS，没有验证被复制的旧正文 hash、结构和当前 Evidence/Snapshot 链。

**修复：** 修订与管理读取共用完整性校验，失效版本不再暴露或复制；只回读引用对应的快照区间，不加载整个快照。JSON 总界限按合法块和引用上限计算，避免误删超过 64 KiB 的合法重复引用。

**验证：** 最新知识上下文 10 项通过，包含损坏 JSON、陈旧快照、公开读取过滤、大段合法引用读写；捕获仓库 4 项与相关 mypy/ruff 通过。

**教训：** 新版本确认必须验证旧版本依据；有界校验的总上限必须容纳已有契约允许的合法数据。

## 源码审计重复解析超过时间预算（2026-09-09）

**现象：** 新增前端模块后，生产源码审计从基线 29.6 秒增加到约 38 秒，超过原 30 秒门槛。

**修复：** 每次审计创建独立解析缓存，仅同路径且文本完全一致时复用；退出时恢复前一层缓存，fixture 之间不复用。

**教训：** 规则规模增长时先消除相同输入的重复工作，缓存必须保留输入身份并隔离不同审计。

## 可选来源读取超时与连接池清理（2026-09-09）

**现象：** 临时锁竞争使可选上下文读取失败；连接池替换连接时再次设置 journal mode，会在外部独占锁期间超时并丢失池槽位。

**根因：** 临时不可用与完整性错误共用异常；清理过程重复执行可能获取写锁的 PRAGMA。

**修复：** 仅识别 deadline 和 SQLite 临时锁错误，省略本次可选来源并保留原历史；未知和完整性错误继续失败。替换连接沿用数据库已有 journal mode，避免在清理时读写数据库。

**验证：** 定向 4 项通过，包含真实独占锁、缺表错误不降级、恢复后池容量保持 4；相关 mypy 通过。

**教训：** 可选能力降级必须区分暂时不可用与验证失败；失败清理本身也要受时限和资源守恒约束。

## 新协议续聊遗漏持久化身份与界面路由（2026-09-09）

**修复：** 接纳保留原对话 ID，挂载准备重点管理路由，并补已有对话重放、跨对话冲突、只读观察与确认代次的真实应用集成测试。

**教训：** 模块测试通过后仍需从实际产品入口验证身份传递、路由注册和保存结果。关闭重开应只读取原任务，不能新建执行。

## 可选上下文来源与历史轮次边界（2026-09-09）

**现象：** P4 审查发现，偏好放在当前请求之后可能覆盖请求；摘要切在轮次中间会让保留回复变成孤立消息；Captured Source 分支误查面试笔记不存在的软删除字段。

**根因：** 新来源接入时未完全沿用最终消息顺序、原历史分组和面试笔记实际删除契约。早期 Knowledge 测试只覆盖无 Capture metadata 的来源。

**教训：** 来源适配测试必须包含真实来源元数据分支；压缩历史必须保持原分组，不只比较文字或总预算。验证记录见 [P3B–P5 计划](superpowers/plans/2026-09-09-harness-p3b-p5-delivery.md)。

## 执行状态跨页面后缺少发送门禁与完成回填（2026-09-09）

**现象：** P3A 审查中发现，Haru 仅从服务端读到 running 时仍可用 Enter 发起请求；执行 A 切到 B 再返回 A 后，旧 stream 完成在展示接口失败时不能回填最终消息。

**根因：** 发送门禁只看本地 loading；旧 stream 的可见代次失效后只刷新会话列表，依赖可选 Timeline 恢复内容。

**修复：** 两个外壳和共享发送入口均检查 running execution；返回原会话后的完成回读持久消息及 Pending，落地前再次核对会话、可见代次和当前请求所有权。返回失败提供错误提示。

**验证：** Haru 远端执行禁用输入、共享发送拦截、后台完成回填及回读期间切换会话均有定向用例；先复现缺失门禁与缺失回读，再验证修复。完整本期记录见 [P3A 计划](superpowers/plans/2026-09-08-harness-p3a-turn-control.md)。

**教训：** 服务端执行状态必须覆盖所有发送入口；可选展示接口不能成为恢复已提交结果的唯一途径。

## 展示失败回退后缺少恢复入口（2026-09-08）

**根因：** 刷新入口依附操作卡片；Hook 虽有刷新方法，实际外壳没有独立恢复按钮。之前测试中的辅助按钮不能证明产品入口存在。

**修复：** 会话所有者暴露按会话隔离的展示失败与刷新状态，Pilot 和 Haru 共用独立恢复提示。重试仅调用展示 GET，进行中禁用按钮，重复失败保留入口，成功后隐藏；旧请求不能覆盖当前状态。

**验证：** 真实 Haru 组件先复现入口缺失，再验证无 Pending / Undo 时的可见按钮、重复失败、禁用防连点和恢复成功；相关前端 49 项、TypeScript、构建与独立 CR 通过，既有大 chunk 提示保留。审查发现的旧卡片和 Pending 刷新入口防连点缺口也已修复。

**教训：** 故障恢复必须从产品可见入口完成闭环，不能仅验证 Hook 暴露的函数可调用。

## 展示刷新失败遮住最新持久消息（2026-09-08）

**现象：** Pilot / Haru 成功加载一次展示后，后续展示请求失败，已保存的新问题和回复仍被旧快照遮住。

**根因：** 失败分支未清除缓存投影，而过期投影只追加 transient 消息，不包含新增持久消息。

**修复：** 当前请求失败时清除展示快照，回退到会话所有者的最新消息；过期请求的失败不影响新请求。请求期间仍保留原操作节点，手动刷新成功后恢复服务端展示。

**验证：** 新增回归先复现失败，再验证持久消息回退、刷新恢复和旧请求拒绝隔离；相关前端 47 项通过。迁移基线为新仓库 `origin/master`，顺序迁入 `608272c → bda0ef7 → ecaa2b5`，对应 `a0e9519f → 478568b3 → 64c988e8`。

构建（含 TypeScript）与独立子代理 CR 通过；内置浏览器在临时数据库、假 Provider 下先加载成功展示，再注入展示 GET 503，拒绝建议后的最新持久回复正常显示。后端代码与迁移前一致，本次未重跑后端全套、完整发布 gate、Docker 或真实 Provider 验收；既有前端基线约束与并发撤销风险仍保留。

**教训：** 快照的加载中保留策略必须有失败出口；首轮加载失败测试不能替代已有缓存后的刷新失败测试。

## 未知录入另建后重开丢失恢复入口（2026-09-08）

**现象：** 未知提交选择承担风险另建后，关闭重开表单不再显示旧提交；新增恢复存储也未与既有隐私审计契约对齐。

**根因：** 常驻表单的 `bypassed` ref 超出单次打开周期；恢复存储直接序列化开放的运行时对象，审计没有获批恢复流程的限定规则。

**修复：** 每次打开清空跳过标记；读写恢复记录校验工作区、请求键、封闭字段和类型，拒绝凭据及额外参数。审计仅认可已审查适配器的固定路径与内容摘要，保留全局敏感存储检查和负向测试。

**教训：** 关闭、重开与刷新是不同生命周期，均需验证未知结果仍可恢复。获批本地恢复不是持久化任意 AI 状态或凭据的许可。

## 单条录入衔接中的来源读取与导航缺口（2026-09-08）

**现象：** 开启工作区鉴权时 JD 请求缺少访问令牌；历史保存时间没有时区；新建或重复提示返回的投递若不在列表缓存中，无法立即打开准备页。

**根因：** JD service 独立调用 fetch 未复用 auth headers；SQLite UTC 时间直接序列化为无时区字符串；详情导航只从列表缓存解析身份。

**修复：** JD 请求使用现有 authHeaders，历史时间按 RFC3339 标记 UTC；新增入口在导航前纳入返回身份并保留后续列表重取。关闭表单后的旧异步回调增加代际检查，避免意外导航。

**教训：** 创建成功、列表刷新和资料读取是三个独立结果，必须分别验证恢复路径。来源字段不因此变成可访问的网址；令牌只用于本地 API，不写入草稿或来源。

## 用户修改确认参数后，模型建议改回旧值（2026-09-07）

**状态：已实现确定性回执边界；验证与限制见 [P0 记录](../artifacts/2026-09-08-harness-p0/verification.md)。**

**现象：** 用户把签字费从10000改为8000、远程办公从两天改为一天并批准后，模型仍可能把新值解释为保存错误，建议恢复原请求。

**根因：** 续答已有实际批准参数和工具结果，但缺少“差异来自用户主动修订”的明确语义；原始用户请求仍在上下文中，模型可能错误地把旧请求当作最终意图。

**修复：** 用户合法修改参数且规范化后与原提案不同、Ledger 可靠证明提交成功时，结束本次确认后的模型续答。回执从原终态结果构造，与 ToolMessage 原子保存；策略绑定原操作、请求指纹与结果摘要，重启恢复和重复确认不再进入模型。原提案、HITL、Undo 和独立新请求保持可用；等价编辑与失败沿用原分支。决定见 [ADR-0006](architecture/decisions/0006-edited-confirmation-receipts.md)。

**实际验收：** 之前两版提示词各有一次真实样本反向，最严重样本生成恢复旧值的 Pending。本次可控测试先在旧代码证明额外模型调用，再验证成功编辑后的零调用与独立进程恢复。真实模型固定两个隔离 Offer：初轮仅文字确认，在原对话各补一次明确确认后均进入系统 Pending；编辑为 8000/一天后，sync/SSE 和交叉重放通过，总调用 6 次（上限 8），确认阶段零调用。首轮结果全部保留，不隐去未进入 Pending 的情况。

**教训：** 需要确定性保证的确认边界必须由可信业务事实控制，不能依赖模型措辞。业务提交成功与回执交付必须分别恢复，不能直接返回未保存的成功字符串。停止自动续答仅适用于本次成功编辑确认；模型文字二次确认、虚构按钮和多入口展示属于独立问题。

手动 mutation 只失效题库而非 due 缓存；表单未关联预填；独立来源查询的加载状态被解释为领域不可用；展示层复用机器路径/错误状态域。Runtime 校验原提案后未将实际批准参数投影到 continuation，且 `None` 的 Undo 更新语义为保留旧值。

### 修复
新增/编辑/删除同时刷新 due；新建 Offer 按字段预填并保留手改；未可执行任务等待来源查询完成；日期/时长缺失明确展示。路径只做中文展示，原证据身份不变；根级 import_review 不进入新候选/新选择，但历史证据仍可重校验。确认续跑仅修改脱离持久化的消息副本；成功/失败无 Undo 用空对象清旧 owner，拒绝仍保留原 Undo。撤销错误显示冲突或核对结果提示，不放宽 CAS。

### 教训
缓存依赖、加载态与不可用态、展示身份与执行身份必须分离。保留原提案审计与历史证据兼容。Undo 更新必须区分保留、清除和替换。组件回归、sync/SSE 确认集成及历史来源重校验覆盖上述边界。

### 尚未关闭
U01 模型文字二次确认/备注能力描述、U02 unknown_tool、U05 标签页崩溃、U10 谈薪算术与擅自承诺、U12 请求中止/结果待确认尚无足够根因证据。本次不改变模型策略、不自动重试、不撤销未知结果，不宣称全部走查问题已解决。历史已失效的 Undo 数据不批量重写。

## 日程时区偏移（2026-09-07）

**现象：** Pilot确认15:00后，日历显示23:00；带非零offset的API输入亦受影响。

**根因：** SQLite DateTime丢弃offset而保留wall time；仓库未先换算UTC，API回读又给无时区值补UTC。页面通常提交Z时间，因而掩盖了另一入口的问题。

**修复：** 日程仓库普通/绑定/scoped创建和更新统一将scheduled_at、remind_at换算成UTC再写入；naive保留既有UTC含义，参数原文、事务所有权和Provider契约不变。未对无法恢复原始offset的历史行做批量迁移。

**验证边界：** 新增东八区、负offset、跨日、UTC、naive、提醒和回滚测试；API覆盖创建/更新/列表回读。复现用例先在旧实现出现8个偏移失败。模型虚构按钮或误解用户修订是独立回复质量问题，不属于本条修复。

**教训：** 以存储边界保存同一时刻，不只在显示层做时区转换；同一功能必须覆盖页面与工具输入的不同时间编码。

## 多标签页覆盖待恢复提交（2026-09-08）

**现象：** 两个标签页同时更新待恢复提交时，后写入的数组可能覆盖另一个请求，导致恢复入口丢失；不会因此自动重复执行请求。

**根因：** `chatSubmission.ts` 将所有请求存放在一个 localStorage 数组，增删和接纳更新均先读后写。localStorage 单次写入原子性不能保证整个读改写过程原子。

**修复：** 按 request ID 独立保存恢复身份，每次只修改对应键。旧数组保持只读；对应独立记录覆盖旧值，删除旧请求用无正文标记抑制旧入口。快照按 ID 排序以保持 React 订阅稳定；存储不可用时保留本标签页内存恢复。

**验证：** 在第一个标签页写入前确定性插入第二个标签页新增请求，覆盖新增、标记接纳、删除请求及按会话删除四种交错；旧实现全部丢失第二个请求，修复后均保留。另覆盖旧数据重新加载、跨标签事件订阅、稳定快照和存储写入失败。

**教训：** 多标签页共享的集合不要通过全量读改写维护独立请求；请求幂等执行与客户端恢复入口持久化需要分别验证。

**剩余边界：** 本修复隔离不同 request ID 的写入。同一 ID 在两个标签页并发接纳和遗忘仍可能留下多余恢复入口；这是只读恢复提示，不会触发自动执行。暂不为此引入永久终态标记或异步事务存储。

## PowerShell 门禁在原生命令失败后仍显示通过（2026-09-10）

**现象：** pytest、前端构建、`oc smoke` 或可选子门禁返回非零退出码后，PowerShell 发布入口仍继续执行并显示 `Release gate passed`；发布入口与 local smoke 还会重复构建前端。

**根因：** `$ErrorActionPreference = "Stop"` 不会自动把 Windows PowerShell 原生命令的非零退出码变成终止错误；父脚本也未检查子 PowerShell 的退出码。local smoke 无复用本轮成功构建的显式参数。

**修复：** 发布、local smoke、安装及 Docker PowerShell 入口逐项检查原生退出码并终止；Shell/PowerShell local smoke 默认构建，发布入口只在构建成功后传 `--skip-build` / `-SkipBuild`，跳过时仍要求存在 `web/dist/index.html`。真实 CLI 启动、HTTP、HITL 与业务 smoke 覆盖保留。

**验证方式：** 隔离命令夹具执行实际门禁脚本，注入各步骤非零退出码，验证停止后续步骤、父入口非零且无成功提示；同时覆盖单次构建、独立 smoke 默认构建、缺产物与参数传递。修复前已复现失败仍显示通过和双构建。

**教训：** 成功日志不是成功证据；每层脚本必须传播失败。构建产物存在不等于匹配当前代码，复用需要同一成功构建的上下文。

**同轮走查补充：** PowerShell local smoke 原先只停止启动器，真实通过或启动超时后均可留下 uv/oc/Python 子进程。改为清理本次启动器的进程树、限时等待退出，始终恢复调用者数据目录环境；清理失败不显示通过。回归覆盖成功/失败后的清理和清理本身失败。首次新虚拟环境冷启动曾在依赖字节码写入时超时，保留失败记录，不调整健康检查超时。
