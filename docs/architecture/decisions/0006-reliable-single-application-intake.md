# ADR-0006：单条岗位录入的原子创建与恢复

- Status：Accepted
- 日期：2026-09-08
- Decider：用户确认任务 A 及三个补充契约，并授权实施。
- 依据：任务 A 交接方案；[现有 JD 版本契约](../../superpowers/specs/2026-08-05-application-jd-versions-design.md)。

## Context

单条录入需要一次确认保存投递和首版 JD，并在响应丢失后安全恢复。现有 JD 版本幂等只覆盖已有投递内的版本写入，不能避免重复创建投递。

## Decision

### 创建与回执

- 扩展 `POST /api/applications`，新增 `idempotency_key` 和可选 `initial_jd: {jd_text, source_url}`；提供首版 JD 必须传创建幂等键。旧请求不传键、也不传 JD 时保持默认 `applied`、`source=web` 和原响应结构；CLI、Pilot 默认行为不变。
- 新录入表单默认 `pending`，允许明确选择补录已投递及既有其他状态；公司和岗位拒绝纯空白。
- 协调服务用一个 SQLite `BEGIN IMMEDIATE` 事务，绑定现有 Application 仓储和 JD 服务的 Session，原子提交 Application、可选 JD v1 和创建回执；任何失败回滚。
- 以校验和默认值补齐后的创建内容生成排序 JSON 的 SHA-256 指纹，包含 JD 及规范化来源 URL。JD 正文保留原始字符，不裁剪或做 Unicode 规范化。
- 相同键和指纹返回原结果（`200`），首次创建 `201`，同键异参 `409 application_creation_conflict`。锁竞争超时返回 `503 application_creation_retryable`，客户端继续使用原请求恢复。
- 回执以数据库工作区标识、`create_application`、客户端随机键组成唯一约束，持久保存请求指纹、结果 JSON、Application ID、可选 JD ID。回执不随资源删除而释放键。新式响应保留 Application 字段，并增加 `jd_version_id`。

### 当前工作区边界

当前运行时是单数据目录、共享访问令牌的本地工作区，没有独立用户或工作区成员表。`application_creation_workspace` 在当前数据库保存一个随机稳定标识，`GET /api/applications/creation-context` 在既有 auth 中间件保护下返回它。回执和重复检查均限于这个数据库；不从客户端接受可切换归属的 scope。

新表单携带 `expected_scope_id` 作为归属一致性前提；若服务端数据目录在表单打开后发生切换，返回 `409 application_creation_scope_conflict`，不向新工作区写入。该字段不能用于选择工作区，也不改变既有调用兼容性。

将来若增加多用户共享数据库，必须同步改造这两个接口、唯一约束及浏览器恢复命名空间，不能继续将整个数据库视作单一授权范围。

### 恢复与确认

- 填写、核对、重复检查和取消均不创建业务记录。来源网址只保存及展示；表单提供显式复制岗位链接到本版来源的按钮。
- 发送前按工作区标识和随机键保存原请求及提交状态到本地存储，不保存凭据；存储失败时不发送。
- 超时、断网、裸服务端失败均按结果未知处理；关闭或刷新后重新打开表单，优先展示原提交并重放原请求、原键。稳定的参数校验失败才允许返回修改。
- 用户可以明确承担重复风险另建草稿；旧未知记录仍保留供后续恢复。清除本地存储或换设备不保证自动恢复，需先检查已有记录。
- “另建”的跳过标记仅在当前表单打开期间有效；关闭重开（包括父组件关闭）必须重新提供旧未知提交的恢复入口。
- 本地恢复仅允许 `request + status` 封闭结构；请求只含创建字段和首版 JD，不接受凭据、确认令牌、传输 headers 或任意额外字段。保存和读取均校验工作区、请求键及字段类型；损坏记录保留但拒绝自动重放，不静默裁剪原请求。
- 隐私审计仅对 `applicationCreationRecovery.ts` 的已审查内容摘要开放例外，并由运行时封闭结构测试与负向 fixture 约束。移动路径、绕过校验或追加泄露代码都会失去例外；修改适配器需重新审查后更新摘要，其他模块的全局隐私规则不变。
- 成功后清理本地恢复记录，将返回身份交给现有投递准备页；不自动调用模型、生成材料或推进状态。列表缓存先纳入新身份，避免列表重取延迟阻断导航。

### 重复提示

- 查询当前工作区所有业务状态，排除软删除记录；失败显示“未能完成检查”，用户仍可明确继续。
- URL 只去除首尾空白后精确比较，保留查询参数，不访问网页。
- 公司、岗位分别做 NFKC、大小写统一、连续空白合并；两字段均相等或短文本为长文本前缀时提示，前缀要求短文本至少两个字符。
- 优先 URL 相同、名称完全相同、名称前缀匹配；同级按更新时间倒序（同时间按 ID 倒序）。最多 20 条，并返回 `has_more`。不自动合并或恢复记录。
- 历史展示补齐版本、保存时间、保存入口、版本来源和原文；沿用旧 JD 版本链及实际投递快照，不回填、重写历史。

## Consequences

新增两张小表，无破坏性迁移。回执长期占用少量空间；本地恢复记录在待确认期间含用户填写的岗位及 JD，需要由用户管理浏览器存储。重复提示当前为数据库内只读扫描，适合单用户规模；扩展规模时可加索引候选筛选，但不得改变匹配语义。

## Alternatives Considered

1. 前端先创建投递再保存 JD：失败会遗留半完成记录，拒绝。
2. 仅进程缓存幂等结果或仅复用 JD 版本幂等：重启或重新创建投递仍会重复，拒绝。
3. 公司、岗位或 URL 作为唯一身份：会合并不同机会，拒绝。
