# ADR-0006：修改确认成功后使用确定性回执

Status：Accepted。日期：2026-09-08。

Decider：用户已授权实施 Harness 交接方案 P0。
依据：方案提交 `5b3bbb2` 的 §5、§15.1，以及现有人工确认、Ledger 与交付所有权协议。

## Context

用户主动修改写操作参数后，模型仍可能把原请求当作最终意图，提出恢复旧值。
既有上下文说明在真实模型检查中仍有反向提案；仅强化提示词无法保证行为。
业务成功与回复交付由不同边界保存，停止模型也必须保留可恢复的原操作回执。

## Decision

合法编辑对工具规范化后的有效参数构成实际变化时，为本次批准绑定版本化回执策略。
可信 Ledger 证明提交后结束本次确认后的自动续答，由代码根据当时的终态结果生成说明。
原提案、最终批准参数和提交事实保持独立；回执与原 ToolMessage 沿用原子交付、Pending
清理和 Undo。重放与过期交付恢复读取原策略，不从当前请求或当前业务对象猜测历史。

策略以增量列及终态标记保存，并绑定原操作、确认请求指纹、终态摘要和展示字段。
策略关联不完整时拒绝降级到模型。旧记录不回填推测的编辑意图，不重写历史回执。
回滚须保留新策略的读取与恢复能力；不支持新策略的旧二进制不可直接接管这些操作。
这是部署约束；本次没有新增能够阻止任意旧二进制打开数据库的启动锁。
回滚应停止服务接纳新确认、备份数据库，再使用保留本策略 reader/reconciler 的修复版本。
不能仅切回旧可执行文件后恢复写入，也不能删除策略列或 marker 来绕过兼容边界。

## Consequences

编辑确认成功后不再出现模型反向 Pending，也不会自动执行后续模型步骤。
用户可以发起独立新请求继续任务。原样批准、等价编辑和失败沿用既有行为。
新增迁移须覆盖空库、历史库与中断重启；诊断 Journal 不成为回执可靠性的依赖。
原写入成功与撤销冲突分别表达，不能用撤销失败否定原提交事实。

## Alternatives Considered

- 继续强化临时系统说明：已有真实样本表明仍会反向提案，无法提供确定性保证。
- 执行成功后直接返回字符串：绕过交付持久化与所有权，响应丢失后无法一致恢复。
- 全面终止所有确认后的续答：改变原样批准与其他现有分支，超出本期范围。
