# Offer 比较与谈薪准备界面收口设计

## 1. 背景

Offer 比较与谈薪准备已经完成业务实现、严格证据门控、UI/Pilot 双入口以及真实浏览器验收。当前功能可以工作，但新增界面仍大量使用原生 HTML 控件和连续文本：

- 自定义比较维度像临时管理表单，输入框与操作按钮缺少一致的层级。
- Offer 横向对比只有基础表格，不能快速识别两份 Offer 的关键信息和缺失信息。
- 谈薪准备把来源、用户输入、AI 建议、证据和历史连续堆叠，阅读路径不清晰。
- Pilot 的 Offer 询问、用户选择和确认过程缺少明确的对话状态。
- 当前验收截图虽然完整，但不能体现成熟产品应有的视觉质量。

本设计采用已经确认的 A 方案“结构化准备工作台”。它是保留式优化，不改变 OfferPilot 的整体布局、路由、业务流程或安全语义。

## 2. 设计目标

1. 让普通求职者能按“看清事实、填写目标、确认来源、审阅建议、确认保存、查看历史”的顺序自然完成谈薪准备。
2. 让 UI 和 Pilot 两个入口具有一致的视觉语言，同时继续隔离各自草稿、幂等键和 Proposal。
3. 明确区分 Offer 事实、用户输入、AI 建议、证据引用和用户最终保存内容。
4. 保留“AI 只提供建议，最终决定由用户作出”的产品边界。
5. 使用现有 Ant Design、OfferPilot 设计令牌和共享组件完成收口，不增加新的 UI 依赖。
6. 在亮色和暗色模式下保持可读性，发布截图使用亮色宽屏。

## 3. 非目标

- 不修改后端、API、数据库迁移、Provider 输入或 AI 契约。
- 不改变 Offer 比较维度、证据路径、Proposal 终态、幂等和重试语义。
- 不增加 Offer 排名、推荐、匹配分或接受/拒绝建议。
- 不重做左侧导航、AppShell 主布局或 Pilot 整体布局。
- 不改版现有单 Offer“谈薪教练”；本轮只验证它仍可正常使用。
- 不增加自动保存、自动生成、自动确认或跨领域写入。

## 4. 视觉方向

### 4.1 设计判断

这是面向普通求职者的高信任决策辅助界面。视觉语言应当专业、清晰、克制，避免营销页式装饰、过度渐变、玻璃效果和大幅动画。

- 设计变化：中低，保留现有信息架构。
- 动效强度：低，只用于控件反馈、展开收起和状态切换。
- 信息密度：中高，优先提高扫描效率而不是增加空白。
- 品牌强调：继续使用现有紫色作为唯一主要强调色。

### 4.2 形状与层级

- 输入框和主按钮高度统一为 40px。
- 表单控件使用 8px 圆角。
- 内容卡片使用 12px 圆角。
- 页面级面板使用 16px 圆角。
- 用留白、浅色表面和轻微阴影建立层级；边框主要用于输入、分隔和选中状态。
- 每个阶段最多保留一个紫色主操作，其他操作使用次级、文字或危险按钮。
- 所有交互区域至少提供 40×40px 的有效点击范围。

### 4.3 动效

- Hover、按压、选中和折叠使用 150 至 200ms 的 CSS 过渡。
- 只过渡 `opacity`、`transform`、`background-color`、`border-color` 和 `box-shadow` 等明确属性，禁止 `transition: all`。
- 按钮按下使用轻微缩放或位移反馈。
- 遵守 `prefers-reduced-motion`，不增加自动播放动画。

## 5. 页面设计

### 5.1 Offer 卡片

Offer 卡片继续出现在 Offer 中心，不改变卡片网格。

卡片内容按以下层级展示：

1. 公司名称与 Offer 状态。
2. 岗位名称。
3. 固定月薪与计薪月数。
4. 年度现金事实、签字费、期权、截止日期和投递归属。
5. 操作区。

操作层级固定为：

- 主操作：“开始谈薪准备”。
- 次操作：“谈薪教练”。
- 辅助操作：“详情”。

三个入口继续调用现有回调，不改变含义。卡片选中状态、Offer 状态色和拖入 Pilot 的行为保持不变。

### 5.2 自定义比较维度

维度管理区改为紧凑的设置分组。每个分组包含：

- 维度名称和是否参与本次比较。
- 每个 Offer 的公司名和值输入框。
- “保存值”“清除值”和“归档维度”操作。
- 未填写值的明确状态。

交互约束保持不变：

- 最多选择 8 个维度。
- 空值继续表示“尚未填写”，不能写入“无”“未知”等伪事实。
- 清除值仍调用既有 DELETE 接口。
- 归档维度不改变历史 Proposal 的冻结快照。

### 5.3 Offer 横向对比

横向对比仍使用表格，不加入评分或排名。

表格改进：

- 第一列固定为维度名称。
- 每个 Offer 的表头展示公司、岗位和固定薪资摘要。
- 固定字段与自定义维度分组展示。
- “尚未填写”使用低强调文本或标签，不伪装成事实。
- 表格支持宽屏和横向滚动，保持键盘可达。
- 底部为每份 Offer 提供“开始谈薪准备”入口。

返回 Offer 中心的入口保留在页面标题之前，按钮层级降为文字按钮。

### 5.4 谈薪准备工作台

`OfferNegotiationDrawer` 保持当前挂载位置，不改路由和主布局。内部按以下顺序组织。

#### A. 页面标题

- 标题：“为 {公司} 准备谈薪”。
- 说明：“整理事实、问题和表达草稿，不替你决定接受或拒绝 Offer。”
- 关闭入口。
- 当前来源状态标签。

#### B. Offer 摘要

首屏只展示最有帮助的高频事实：

- 岗位。
- 固定月薪与计薪月数。
- 截止日期。
- 关键自定义维度摘要。

福利、备注、期权和其他字段放入“查看完整来源”折叠区。折叠区仍展示真实冻结快照，不重新读取或替换历史数据。

#### C. 沟通信息表单

三个字段保留现有语义：

- 本次沟通目标。
- 主要顾虑。
- 沟通场景。

所有字段使用标签在上、控件在下、错误在控件下的标准结构。禁止用 placeholder 代替标签。

#### D. AI 输入确认

第一次点击后仍执行现有 preview 请求。预览成功后显示产品内 `ConfirmationPanel`，内容包括：

- 即将发送给 AI 的 Offer 冻结事实。
- 用户填写的目标、顾虑和场景。
- AI 不会替用户作出的决定。
- “返回修改”和“确认生成”操作。

第二次确认后才调用 Proposal 生成接口。该设计替代浏览器原生 `window.confirm`，但不减少确认次数，也不增加请求。

#### E. Proposal 审阅

四类 Proposal 分区保持不变：

- 沟通目标。
- 待澄清问题。
- 建议表达。
- 沟通前检查项。

每个建议块显示为独立审阅卡：

- 选择框和建议正文。
- “为什么建议”说明。
- 选中后出现的可编辑区域。
- 中文证据标签。
- 可展开的原始证据路径和逐字摘录。

选中状态必须同时通过背景、边框和选择框表达，不能只依赖颜色。

#### F. 人工确认和保存结果

- 未选择任何建议时，确认按钮禁用，并显示就地说明。
- 确认按钮显示本次将保存的条目数量。
- 保存前继续执行现有人工确认。
- 保存成功后展示用户实际选择和编辑后的最终内容。
- 不展示未选择的建议为“已保存”。

#### G. 历史记录

历史记录不再显示为“查看 4”一类无上下文按钮。当前 API 没有暴露 Proposal 生成时间，因此本轮不伪造该事实，也不为视觉优化扩展 API。每条记录展示：

- 记录编号；已确认 Brief 存在时展示真实 `confirmed_at`。
- Offer 公司与岗位。
- Proposal 状态。
- 是否已确认保存。
- 来源是否变化。

点击后进入现有只读历史详情。历史详情必须继续使用冻结快照，不能显示当前 Offer 事实替代历史事实。

### 5.5 Pilot 入口

Pilot 继续要求用户主动点击“准备谈薪”，不自动列出 Offer，不自动调用 AI，也不写入 Chat。

Pilot 的视觉状态分为：

1. 询问卡：说明为什么需要选择 Offer，并列出可选 Offer。
2. 回答确认卡：展示用户已选择的 Offer 及“更换”“继续准备”操作。
3. 生成前确认卡：复用谈薪准备工作台的冻结来源与人工确认内容。
4. 结果状态：继续使用同一 Proposal 审阅与历史组件。

Pilot 与 UI 入口继续通过 `entrypoint` 隔离草稿、幂等键、Proposal 和历史。视觉复用不能合并业务状态。

### 5.6 单 Offer 谈薪教练

现有“谈薪教练”入口保留。只允许因共享 Offer 卡片样式产生的视觉调整，不修改 Chat 面板、能力入口、上下文绑定或写入确认逻辑。

## 6. 共享组件与代码边界

### 6.1 继续复用

- `SourceStateTag`：当前来源、已冻结来源、来源已变化。
- `ConfirmationPanel`：AI 输入确认和保存前确认。
- Ant Design 的 `Button`、`Input`、`Input.TextArea`、`Checkbox`、`Tag`、`Collapse`、`Alert`、`Table`、`Empty`、`Skeleton` 和 `Tooltip`。

### 6.2 建议拆分

保留 `OfferNegotiationDrawer` 的请求和状态协调职责，将展示拆分为聚焦组件：

- `OfferSnapshotSummary`：当前或冻结 Offer 摘要与完整来源。
- `NegotiationBriefForm`：目标、顾虑和场景。
- `NegotiationProposalCard`：单条建议、选择、编辑和证据。
- `NegotiationHistoryList`：历史摘要和只读导航。
- `PilotOfferSelectionCard`：Pilot 的询问与选择确认。

组件可放在 `web/src/components/offer-negotiation/`。只在一个位置使用且足够短的展示片段可以保留在父组件中，避免为拆分而拆分。

### 6.3 样式

- 使用 CSS Modules 和现有 Ant Design token，不继续增加大段内联 `style`。
- 样式名称表达语义，不编码 Proposal 状态机。
- 不把 Provider 错误码、API 枚举或证据路径映射写入 CSS。
- 不增加第三方样式库。

## 7. 状态与错误呈现

前端状态机和 HTTP 语义保持原样，视觉呈现统一如下。

| 状态 | UI 表现 | 允许操作 |
| --- | --- | --- |
| 编辑输入 | 正常表单与当前来源 | 编辑、预览、关闭 |
| Preview 已冻结 | 冻结来源标签与确认面板 | 返回修改、确认生成 |
| `202 generating` | 等待确认提示，输入冻结 | 使用原尝试重试 |
| `502 offer_negotiation_provider_error` | AI 服务结果待确认，输入冻结 | 使用同一 key 重试 |
| `502 offer_negotiation_unverifiable` | 建议不可验证 | 重新开始新 Attempt |
| `safe_empty` | 正常空状态，不显示为系统故障 | 返回或查看历史 |
| 来源变化 | 来源已变化标签和只读提示 | 查看历史，不保存 |
| 确认结果未知 | 保存结果待确认 | 使用原 confirmation key 重试 |
| 历史已确认 | 只读展示最终保存内容 | 返回历史列表 |

所有错误继续按稳定错误码映射为安全中文文案，禁止展示 Axios message、Provider 原文或服务端内部错误。

## 8. 可访问性

- 表单标签与控件显式关联。
- 表格、折叠区、历史列表和建议卡可以使用键盘完成操作。
- 焦点环在亮色和暗色模式均可见。
- 状态不能只依赖颜色表达。
- 正文、辅助文本、placeholder、禁用态和错误提示满足 WCAG AA 对比度。
- 加载、错误和结果未知使用正确的 `role=status` 或 `role=alert`。
- 动态薪资数字使用等宽数字，避免布局跳动。

- Offer 卡片的主次操作、状态和键盘行为。
- 维度创建、选择、保存、清除、归档和最多 8 项限制。
- 对比表的固定字段、自定义维度、缺失值和不同 Offer 顺序。
- 当前来源、冻结来源和来源变化三类标签。
- 表单必填、输入超限、加载失败和重试状态。
- Preview 只调用一次，确认后才调用生成接口。
- Proposal 四个分区、选择、编辑、证据展开和保存数量。
- `safe_empty`、Provider 未知、契约失败、来源变化和确认未知状态。
- 历史摘要与冻结详情。
- Pilot 询问、选择、回答确认和 UI/Pilot 状态隔离。

### 9.2 挂载与边界测试

- 从 Offer 中心打开谈薪准备，保留正确 Offer 和 `entrypoint=ui`。
- 从 Pilot 主动选择 Offer，保留正确 Offer 和 `entrypoint=pilot`。
- 关闭和重挂载后恢复对应入口的原草稿和幂等键。
- 纯渲染、选择建议、展开证据和查看历史不会产生额外写请求。
- 单 Offer“谈薪教练”仍绑定正确 Offer 并可打开。

### 9.3 浏览器验收

使用现有真实配置的隔离副本和中文候选人“筱哲”，在亮色宽屏下完成：

2. Offer 横向对比。
3. UI 谈薪准备来源确认。
4. UI Proposal 生成、编辑、确认和历史。
5. Pilot 询问 Offer。
6. Pilot 用户选择回答。
7. Pilot 来源确认。
8. Pilot Proposal 生成、确认和历史。
9. 单 Offer 谈薪教练入口。

每张截图不低于 1440×900，必须逐张检查裁切、空白、滚动位置、敏感信息和关键内容完整性。新的截图替换 `artifacts/2026-08-03-offer-negotiation/` 中对应的简陋截图，并更新发布报告。

浏览器请求继续接受 CDP 审计：

- 前端全量测试、TypeScript 和生产构建通过。
- Ruff、Mypy 和差异检查通过。
- 相关后端契约测试保持通过，确认没有业务语义变化。

任何一个入口、错误状态或历史状态没有完成时，不能宣称本轮 UI 收口完成。

## 11. 破坏性变化与风险

### 11.1 破坏性变化

无 API、数据库、AI 契约或持久化语义破坏性变化。DOM 结构和样式类会发生变化，依赖不稳定 DOM 层级的旧前端测试需要改为基于角色、标签和稳定 `data-testid`。

### 11.2 主要风险

- 展示拆分时意外改变未知结果、重试或确认状态。通过状态矩阵测试和真实流程回归控制。
- 历史界面错误显示当前 Offer。历史组件必须只读取 Proposal 冻结快照。
- UI 与 Pilot 为了复用视觉而错误共享草稿。复用仅限展示组件，业务状态继续按入口隔离。
- 更换浏览器原生确认后减少确认步骤。实现必须保持 preview 后确认和保存前确认两次人工确认。
- 视觉优化导致页面过度留白或滚动过长。宽屏浏览器走查需要同时检查首屏密度和完整流程。
