# 为什么不能让助手一直试到成功？

你只是想查看有哪些面试，助手却反复查找、换个说法再查找，迟迟没有结束。每一步看起来都像在努力，但任务没有新的进展。

除了告诉模型“尽快完成”，程序还需要决定一次任务可以使用多少时间和资源。

**下面的次数与处理方式均为虚构教学示意，不是 OfferPilot 的默认限额，也不是费用测算。**

## 给任务一个可以停下来的边界

假设教学助手有这样几项限制：

| 限制什么 | 想避免什么 |
| --- | --- |
| 同一查询暂时失败后，最多再尝试两次 | 一直重复同一个失败请求 |
| 工具执行有等待时限 | 一直卡在没有回应的操作上 |
| 一次任务有模型调用与总耗时上限 | 不断生成下一步，却始终不收尾 |
| 记录并限制可用的调用额度 | 简单任务意外消耗大量资源 |

这些不是“所有 Agent 都应该设成同一个数字”。上限要与任务复杂度、工具特性和使用成本相匹配。

调用次数、总耗时和费用也不是同一个量。一次模型调用可能包含很多资料；一个工具可能耗时很久；多次便宜的查询也可能累积起来。

## 等用户确认，与卡住不返回不同

助手提出修改建议后，需要等你决定。这是一种有明确原因的等待，界面应该说明“等待确认”，而不是持续显示它正在思考。

如果产品规定确认建议会过期，就应在过期后重新核对条件，而不是自动认定用户同意。等待超时也不能变成绕过确认的理由。

工具卡住、模型反复查询和等待用户答复，因此需要不同的处理，不能全用一个“正在运行”掩盖。

## 达到限额之后，也要交代做到哪里

假设助手已经查到云岚数据的面试，但读取青禾科技的记录连续失败，随后达到了重试上限。可以这样说明：

> 已读到云岚数据的面试记录；青禾科技的记录本次未能读取，所以目前结果不完整。已停止继续尝试，没有修改日程。

这比把部分结果当作全部结果，或只留下一句“任务结束”更有用。

如果限额是在保存请求发出后达到的，还要继续区分已完成和结果未知。停止启动新步骤，不会让已经发出的操作自动消失。

一些系统会在两次模型请求之间检查费用限额，因此最后一次在途请求仍可能产生费用。限额究竟何时生效，要看具体实现，不能把界面上的估算当作任何情况下都精确封顶的承诺。可参考 [Claude 会话预算的说明](https://platform.claude.com/docs/en/managed-agents/sessions)。

## 继续时，不必把所有事再做一遍

你稍后选择继续，可以基于已经核对的状态补做未完成部分。已成功保存的内容不应重做，旧确认是否仍有效也需要检查。

Harness 负责统计使用情况、执行限制、区分等待原因，并在停下时留下可解释的状态。模型可以提出继续尝试的建议，但不能靠不断说“再试一次”越过程序规定的上限。

## 用自己的话说说看

助手已经达到本次重试上限，但模型仍建议“再查询十次”。Harness 应该只因为模型这样说，就取消限额吗？

<summary>看一个参考回答</summary>

不应该。它应落实当前限制，说明已完成和未完成的部分。需要增加额度或继续任务时，应按产品规则处理，并核对状态，而不是让模型自行扩大执行范围。
