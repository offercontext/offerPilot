# 投递跟进信与面试感谢信草稿设计

状态：已批准实施

## 目标

在现有“投递事实与结果”工作区内，把已经冻结的投递档案和用户记录的结果转换为可编辑、可复制的中文沟通草稿：投递后跟进信与面试后感谢信。系统不发送邮件、不猜测联系人、不新增外部连接，也不把草稿当作已经发生的沟通事实。

## 首期边界

- 纯前端、只读派生；不新增 API、数据库、AI/Provider 调用或 Pilot 写工具。
- 草稿只存在于当前 Drawer 会话；关闭或刷新后不恢复，不写入投递、Knowledge、Memory、Story 或日程。
- 用户主动选择类型、冻结档案和可选结果记录后才生成；不自动弹出，不自动复制。
- “面试感谢信”只有在所选投递档案存在已记录的面试阶段结果时可用；不能仅凭未来、进行中或已取消的日程推断面试已经发生。
- 用户必须显式选择一条属于当前投递档案的面试结果；关联日程只按该结果的 `application_event_id` 确定性回读，不独立猜选，也不跨投递档案拼接来源。
- 联系人姓名为空时使用“您好”，不猜测 HR、面试官或招聘经理姓名。
- 生成内容只包含公司、岗位、实际投递时间、明确选择的阶段/结果，以及用户自己填写的沟通亮点；不输出录用概率、排名、薪资事实或下一轮时间承诺。

## 确定性草稿规则

新增纯函数 `applicationCommunicationDraft.ts`，输入已加载的 Application、Submission Snapshot、可选 Outcome/Event 和用户显式填写的收件人、面试亮点，输出 `subject/body/evidenceLabels`。

- 跟进信主题：`关于「岗位」申请进展的跟进`。
- 感谢信主题：`感谢「岗位」面试交流`。
- 公司、岗位来自当前投递信息，并在来源标签中明确披露为“当前投递信息”；冻结档案、结果和日程分别标注，不能把当前可编辑字段伪装成冻结快照。
- 日期来自已加载事实，并以显式的客户端时区偏移渲染为本地日历日期；日期无效时不渲染日期句，不伪造默认日期。
- 用户亮点按 1–240 Unicode code point 校验，逐字进入正文；空值时感谢信保留中性的“感谢本次交流”，不补写虚构话题。
- 输出始终是纯文本，不渲染 HTML；换行固定、结果确定，不读取时钟、随机数或网络。

## UI

在 `ApplicationOutcomeDrawer` 的结果表单和历史之间新增“沟通草稿”卡片：

1. 类型切换：投递跟进 / 面试感谢。
2. 来源选择：冻结投递档案；感谢信必须显式选择属于该档案的面试结果，关联日程由结果确定性绑定。
3. 用户输入：联系人姓名、面试交流亮点。
4. 左侧“事实依据”显示当前选中的公司、岗位、档案、结果或日程；右侧信件纸张展示可编辑主题和正文。
5. 主操作为“复制完整草稿”，另提供“恢复系统草稿”；复制后只显示本地成功提示。

宽屏为事实依据与信件双栏，窄屏改为上下排列；沿用当前青蓝色投递档案视觉，不改变应用详情页布局。所有交互命中区域不少于 40px，键盘可操作；类型切换暴露可感知的选中状态和禁用原因，长来源标签可换行，并使用 `aria-live` 报告复制结果。

## 测试与验收

- 纯函数覆盖两类草稿、无联系人、无效日期、UTC/本地跨日、Unicode 边界、用户亮点、取消日程、结果与档案错配、无输入突变与确定性。
- 组件覆盖显式结果选择、结果与日程确定性关联、类型切换、正文编辑、恢复、复制成功/失败、来源失效后的重新校验、可访问状态、长来源标签和零请求/零写入。
- 真实 `ApplicationOutcomeDrawer` 挂载，确认只复用已有查询，不增加任何读取或写入请求。
- 中文“筱哲”亮色宽屏浏览器走查，截图覆盖跟进信与感谢信；控制台错误为 0，浏览器仅访问本地应用/API。

## 破坏性变化

无。首期仅新增纯函数、组件和现有 Drawer 内的入口。
