# 换一个模型，助手就能直接接着用吗？

既然 Harness 负责把模型和工具接起来，能不能保留其他部分，只换一个模型？可以这样设计，但不能只看新模型能不能正常聊天。

**下面用虚构的模型甲、模型乙说明接入与切换，不评价任何实际模型，也不代表 OfferPilot 已支持这些切换方式。**

## 同一份任务，需要两边都理解的表达方式

用户还是想把云岚数据测试开发的面试，改到 2026 年 9 月 22 日 15:00—16:00。

应用希望模型知道当前任务、可用工具和已有记录；模型则可能返回一段回复，也可能返回查询或修改请求。

不同模型服务可能对这些信息有不同的表达约定。因此 Harness 周边常需要一层适配：把应用的输入整理成该服务接受的格式，再把返回内容解释成应用能够处理的结果。[LangChain 的模型文档](https://docs.langchain.com/oss/python/langchain/models)展示了通过统一接口连接不同模型的做法；这里仅借它说明职责。

| 换模型时要核对什么 | 为什么影响同一项任务 |
| --- | --- |
| 是否支持需要的工具调用方式 | 能回答“应该改时间”，不等于能提出可执行的工具请求 |
| 请求与结果能否正确对应 | 查到的记录要交回正确的调用，不能串到别的操作 |
| 能接收哪些内容、多少资料 | 原先能处理的输入，不一定可以原样照搬 |
| 怎样表示结束、错误或未完成 | 程序需要据此决定等待、继续还是收尾 |

表面格式被统一之后，实际理解能力和行为仍可能不同，不能把“接口接通”当作“效果相同”。

## 程序规则不应随模型随意变化

假设模型乙更积极，收到请求后立刻提出保存。只要本例仍规定写入前需要确认，Harness 就仍要等待确认。

模型甲习惯用长句说明，模型乙喜欢简短表格，可以影响回答形式；但能访问谁的数据、哪份修改已获准、有没有超出运行额度，这些规则不能由模型回答的语气决定。

这正是区分模型与运行支撑的价值：换了提出建议的部分，仍然能检查实际执行的条件。

## 中途换模型，比从新任务开始更难

如果模型服务暂时不可用，应用可能考虑切换到另一个服务，也就是常说的备用模型或 fallback。

切换前要核对已有进度：查询是否完成？是否已经产生待确认建议？保存有没有执行？如果保存结果未知，不能让新模型从头再做一次来“补救”。

还要检查哪些会话内容能够继续使用。模型服务可能要求保留特定的调用关联或返回内容，不能只取聊天文字、随意删掉看不懂的部分，再假定一定能续接。

不能可靠续接时，可以停在明确的状态，说明需要重新准备上下文或人工处理。**切换模型不会把未知结果变成失败，也不会自动继承一份已经改变内容的旧确认。**

## 换完之后，仍然用同一组事情检查

除了正常查询和改期，还要看目标不明确时会不会追问、拒绝后是否仍不保存、工具失败后是否如实说明。

Harness 的适配让不同模型能够进入同一个应用流程；实际表现是否合适，要再通过相同任务和明确标准验证。下一批评估结果可能支持继续使用，也可能说明还要调整，而不是只凭一次回答更流畅就下结论。
