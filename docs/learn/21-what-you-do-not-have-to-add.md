# 做一个 Harness，一定要用很多框架吗？

看到这里，你已经认识了工具、上下文、状态、确认、重试和评估。如果再遇到框架、MCP、Skills、多 Agent 等名字，很容易以为还需要把它们全部装进去，才算做完一个 Harness。

先回到产品要完成的任务。**以下选型情境均为虚构教学示意，不是 OfferPilot 的技术路线变更或框架推荐。**

## 先看缺少哪种能力

| 想解决的实际问题 | 可以考虑怎样补上 |
| --- | --- |
| 查询日程并在确认后修改一条记录 | 清楚的工具、运行流程、确认与保存规则 |
| 每接一个外部服务，都要重复处理接入方式 | 使用合适的连接方式或共同协议 |
| 某类任务总需要同一套方法和参考材料 | 把方法与材料整理成可复用的说明 |
| 两类资料各自很复杂，一起处理难以保持重点 | 先拆任务；必要时再考虑由不同 Agent 分工 |

这些办法对应不同问题，不能互相替代。接好了外部服务，不代表用户已经授权调用；写好了任务方法，也不代表保存失败会自动得到正确处理。

## 框架帮助实现，Harness 描述运行职责

框架或 SDK 可以提供调用模型、组织工具、管理状态等现成功能，减少重复工作。Harness 则是实际围绕模型运行起来的支撑系统，可以由框架、自写代码和现有业务程序共同组成。

选择了某个框架之后，仍要核对它怎样等待确认、保存状态、处理失败，以及哪些职责需要应用自己实现。库的名字不能替代这些检查。

同样，自己实现并不自动更简单或更可靠。关键是当前能力是否适合业务，以及开发者能否理解、验证和维护它。

## 多几个 Agent，也会多出交接工作

假设一个复杂任务需要分别分析简历和岗位要求，再汇总准备建议。可以让不同 Agent 各自处理一部分，也可以先用普通程序分步组织。

如果采用多个 Agent，就要明确每个负责什么、能拿到哪些资料、允许用哪些工具、返回什么结果，以及总共可以消耗多少资源。汇总方还要处理遗漏、冲突和某个分支失败的情况。

一个 Agent 说“建议改期”，不能被另一个 Agent 当作“用户已经确认改期”。分工并不会增加原任务的授权范围。

因此，多 Agent 是一种组织复杂任务的选择，不是 Harness 的必备数量指标。对一项简单查询，把工作交接来交接去，也可能只增加等待和出错机会。

<details>
<summary>想对上几个常见名字，再展开看</summary>

| 名字 | 在这里先怎样理解 | 不能据此推断什么 |
| --- | --- | --- |
| 框架 / SDK | 帮助开发者实现模型调用、流程或其他功能的代码工具 | 接入它就已经满足全部业务规则 |
| MCP | 让 AI 应用与外部工具、资料等按共同约定连接的协议 | 能连接就可以不受权限限制地调用 |
| Skills | 可按任务加载的工作说明与参考资源，也可能包含脚本 | 说明里的要求可以覆盖用户授权和程序限制 |
| 多 Agent | 把部分任务分给不同 Agent，再协调结果 | Agent 越多，结果必然越好 |

MCP 的定位见[官方概览](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)；Skills 的组成与按需加载方式见 [Agent Skills 说明](https://agentskills.io/home)。这些资料用于认识概念，不是本系列的安装前置要求。

</details>

## 区分“产品里的助手”和“帮你写产品的助手”

这组文章讨论的是求职产品里的助手怎样读资料、调用功能和修改记录。让一个开发代理帮助编写 OfferPilot，则是另一条工作线。

给开发代理的协作约定、代码任务和开发工具配置，可以影响开发过程，但不能直接当作产品内 Harness 已经具备的功能。两边都有 Agent，也都可能用到类似机制，实际职责和权限仍要分别看清楚。

到这里，遇到一个新技术名字时，可以先问：它补的是连接、资料、流程，还是分工？当前任务是否需要它？理解这个作用，比把名字全部堆进项目更有用。

## 用自己的话说说看

一个助手没有多 Agent，也没有连接外部 MCP 服务，但能管理上下文、工具调用、确认与执行结果。能仅凭前两项缺席，就说它没有 Harness 吗？

<details>
<summary>看一个参考回答</summary>

不能。Harness 关注围绕模型的运行支撑。多 Agent 和外部连接是按需要选择的扩展，应该根据任务所需的职责是否实现来判断，而不是按技术名词数量判断。

</details>
